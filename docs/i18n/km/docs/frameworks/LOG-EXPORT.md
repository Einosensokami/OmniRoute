ការនាំចេញជាបន្តបន្ទាប់ និងជាបណ្ដើរៗនូវកំណត់ហេតុការហៅរបស់ OmniRoute ទៅកាន់ឃ្លាំងវិភាគខាងក្រៅ។

ផ្ទាំងផ្ទាំងគ្រប់គ្រង Logs រក្សាទុកប្រវត្តិសំណើនៅក្នុង SQLite (`call_logs`) ដែលត្រូវបានកំណត់ព្រំដែនដោយ
ការបង្វិលកំណត់ហេតុ និងរយៈពេលរក្សាទុក។ ការនាំចេញកំណត់ហេតុបញ្ជូនសំណុំកំណត់ត្រាដូចគ្នានេះចេញតាមកាលវិភាគ ដើម្បីឱ្យវាអាចរក្សាទុកបានយូរជាង
មូលដ្ឋានទិន្នន័យមូលដ្ឋាន និងអាចភ្ជាប់ជាមួយទិន្នន័យផ្សេងទៀត។ BigQuery គឺជាគោលដៅដំបូង; ខ្សែដំណើរការនេះជាបញ្ជីចុះឈ្មោះ ដូច្នេះអាចបន្ថែម
គោលដៅផ្សេងទៀតបាន។

## 1. របៀបដែលវាដំណើរការ

```
ម៉ាស៊ីនមេ (ឌិគ្រីប + ផ្ទៀងផ្ទាត់ការកំណត់រចនាសម្ព័ន្ធ, ធ្វើសមកាលកម្មទស្សន៍ទ្រនិច)
  → ចាប់ផ្ដើម IPC → ដំណើរការ exportChild របស់ OS ដែលដាច់ដោយឡែក
    → storage.sqlite បានតែអាន → ការសួរទិន្នន័យ/ផ្គូផ្គង call-log ដែលប្រើរួមគ្នា
      → ផ្ទុកវត្ថុបន្ថែមដោយអសមកាល → prepare()/send() របស់គោលដៅ
        → IPC ជាបាច់ → ម៉ាស៊ីនមេរក្សាទុកទស្សន៍ទ្រនិច → IPC ទទួលស្គាល់
          → បាច់បន្ទាប់; IPC បញ្ចប់ → ម៉ាស៊ីនមេកត់ត្រាភាពជោគជ័យ
```

- **កាលវិភាគ** — កិច្ចការ cron មួយរបស់ `JobRegistry` គឺ `log_export` ដែលកំណត់លំនាំដើមជា `0 * * * *` (រៀងរាល់ម៉ោង,
  UTC)។ វាត្រូវបានចុះឈ្មោះនៅក្នុង `src/lib/initCloudSync.ts`; អាចកំណត់ជំនួសដោយ `OMNIROUTE_LOG_EXPORT_CRON`។
  រាល់ពេលដំណើរការ វានឹងបញ្ចេញទិន្នន័យទៅកាន់គោលដៅដែលបាន**បើក**ទាំងអស់ តាមលំដាប់។
- **ទស្សន៍ទ្រនិច** — `call_logs.rowid` ដែលមានស្រាប់ដោយប្រយោលរបស់ SQLite ត្រូវបានរក្សាទុកសម្រាប់គោលដៅនីមួយៗក្នុង
  `log_export_destinations.cursor_row_id`។ `timestamp` មិនត្រូវបានប្រើជាទស្សន៍ទ្រនិចដោយចេតនា៖ អ្នកហៅ
  អាចផ្ដល់តម្លៃផ្ទាល់ខ្លួនរបស់ពួកគេ ដូច្នេះសំណើដែលយឺតអាចត្រូវបានសរសេរបន្ទាប់ពីសំណើដែលលឿនជាង ដែលបានចាប់ផ្ដើម
  នៅពេលក្រោយ ហើយទស្សន៍ទ្រនិចផ្អែកលើត្រាពេលវេលានឹងរំលងវា។
- **ការបែងចែកជាបាច់** — `batch_size` ជួរដេកក្នុងមួយសំណើ (លំនាំដើម 500), `max_rows_per_run` ជួរដេកក្នុងមួយដងដំណើរការ
  (លំនាំដើម 10000) ដើម្បីឱ្យទិន្នន័យដែលកកស្ទះច្រើនត្រូវបានបញ្ចេញក្នុងការដំណើរការជាច្រើនដង ជំនួសឱ្យការរារាំងតែមួយដង។
- **ការបញ្ជូន** — ទស្សន៍ទ្រនិចនឹងទៅមុខតែបន្ទាប់ពី `send()` បញ្ចប់ដោយជោគជ័យ។ បាច់ដែលបរាជ័យទុក
  ទស្សន៍ទ្រនិចនៅទីតាំងដដែល ដូច្នេះជួរដេកដដែលនឹងត្រូវបានព្យាយាមឡើងវិញនៅការដំណើរការបន្ទាប់។ ការធានាគឺ
  បញ្ជូនយ៉ាងហោចណាស់ម្ដង រួមជាមួយការលុបស្ទួននៅខាងគោលដៅ មិនមែនពិតប្រាកដថាតែម្ដងទេ៖ BigQuery កំណត់សោឱ្យជួរដេកនីមួយៗ
  តាម id របស់ call-log ដែលវាអនុវត្តតាមលទ្ធភាពល្អបំផុតក្នុងចន្លោះពេលលុបស្ទួនរបស់វា។
- **ការការពារការត្រួតស៊ីគ្នា** — ការដំណើរការ cron និង `POST .../run` អាចកើតឡើងក្នុងពេលតែមួយ។ គោលដៅ
  ដែលកំពុងបញ្ចេញទិន្នន័យរួចហើយ នឹងត្រូវបានរំលង ជំនួសឱ្យការបញ្ចេញទិន្នន័យពីរដង (`skipped: true` ក្នុងលទ្ធផលដំណើរការ)
  ដូច្នេះការដំណើរការដំណាលគ្នាមិនអាចផ្ញើបាច់ឡើងវិញ ឬសរសេរទស្សន៍ទ្រនិចថយក្រោយបានទេ។
- **ការស្ដារឡើងវិញបន្ទាប់ពីការសម្អាត** — ប្រសិនបើ `cursor_row_id` ឡើងខ្ពស់ជាង `MAX(rowid)` (តារាងទាំងមូលត្រូវបាន
  សម្អាត ហើយ rowid បានចាប់ផ្ដើមឡើងវិញ) កម្មវិធីដំណើរការនឹងត្រឡប់ទៅ 0 ជំនួសឱ្យលែងមើលឃើញទិន្នន័យជាអចិន្ត្រៃយ៍។

### កម្មវិធីដំណើរការដាច់ដោយឡែក និងដែនកំណត់

រាល់ការដំណើរការគោលដៅនៅលើ Node ចាប់ផ្ដើមដំណើរការកូនរបស់ OS ដែលដាច់ដោយឡែក និងមានអាយុកាលខ្លី (`child_process`
ជាមួយ IPC មិនមែន `worker_threads`)។ ការអាន body, ការញែក/បម្លែង payload JSON ទៅជាស៊េរី, `prepare()` របស់គោលដៅ និង I/O
បណ្ដាញរបស់គោលដៅ សុទ្ធតែដំណើរការនៅទីនោះ មិនមែននៅលើ event loop របស់ម៉ាស៊ីនមេទេ។
មានតែការកំណត់រចនាសម្ព័ន្ធ និងសារវឌ្ឍនភាពតូចៗប៉ុណ្ណោះដែលឆ្លងកាត់ IPC; កំណត់ត្រាដែលបាននាំចេញមិនដែលត្រឡប់ទៅ
ម៉ាស៊ីនមេទេ។ កិច្ចការ cron និងផ្លូវ Run now រក្សាលទ្ធផលសាធារណៈ និងការការពារការត្រួតស៊ីគ្នាដដែល។

ដំណើរការកូនបើក `DATA_DIR/storage.sqlite` ដែលបានកំណត់ដោះស្រាយរបស់ម៉ាស៊ីនមេក្នុងរបៀបបានតែអាន ដោយប្រើ `node:sqlite`
ជាមួយ `busy_timeout=5000` និង `query_only=ON`។ វាមិន import DB singleton ណាមួយ ហើយមិនធ្វើ
ការផ្លាស់ទី schema, ការបម្រុងទុក ឬការធ្វើបច្ចុប្បន្នភាព SQLite ឡើយ។ ការកត់ត្រាវត្ថុបន្ថែមដែលបាត់/ខូច (រួមទាំង
UPDATE សម្រាប់វត្ថុបន្ថែមខូច) នៅតែមានតែក្នុងផ្លូវព័ត៌មានលម្អិតរបស់ dashboard ប៉ុណ្ណោះ។ ផ្លូវទាំងពីរប្រើកម្មវិធីដោះស្រាយ
ព័ត៌មានលម្អិតសុទ្ធដូចគ្នា; ការនាំចេញប្រើការអានប្រព័ន្ធឯកសារដោយអសមកាល និងលំដាប់ដោះស្រាយ artifact → legacy

  អនុញ្ញាតឱ្យមានជួរឈរ clustering ច្រើនបំផុតបួន ហើយលំដាប់មានសារៈសំខាន់៖ filter លើ `api_key_name` តែមួយ
  អាចកាត់ចេញបាន ខណៈដែល filter លើ `status` តែមួយមិនអាចធ្វើបានទេ។
- **ការរក្សាទុក partition ជាជម្រើស** តាមរយៈ `partitionExpirationDays` (0 រក្សាទុកទាំងអស់) ដែលត្រូវបានអនុវត្ត
  នៅពេលតារាងត្រូវបានបង្កើត។

ការកំណត់ទាំងពីរត្រូវបានអនុវត្តនៅពេលបង្កើត។ តារាងដែលមានស្រាប់រក្សាប្លង់ដែលវាមានរួចហើយ ដូច្នេះ
សូមកំណត់ទិសដៅទៅកាន់ ID តារាងថ្មី ប្រសិនបើអ្នកចង់ប្រើការកំណត់ទាំងនេះ។

`tests/unit/log-export-bigquery.test.ts` ផ្ទៀងផ្ទាត់ថា mapper និង schema របស់តារាងនៅតែស្របគ្នា
ដូច្នេះ column ថ្មីរបស់ call-log មិនអាចត្រូវបានលុបចោលដោយស្ងាត់ស្ងៀមនៅពេលនាំចេញនោះទេ។

Batch ត្រូវបានបែងចែកជា chunk ដោយផ្អែកលើ **ទាំង** ចំនួន row និងចំនួន byte ដែលបាន serialize។ ចំនួន row តែមួយមុខគឺមិនគ្រប់គ្រាន់ទេ
នៅពេល payload ត្រូវបាននាំចេញ៖ row ចំនួន 500 ដែលផ្ទុក prompt អាចមានទំហំរាប់សិប megabyte ហើយ insertAll
បដិសេធ request ដែលមានទំហំលើសពី 10 MB។ Chunk ត្រូវបានបិទនៅពេលដល់ 500 row ឬ 9 MB ដោយយកលក្ខខណ្ឌណាដែលកើតឡើងមុន។

នោះគឺជាការផ្លាស់ប្តូរទាំងមូល៖ ការរក្សាទុកទិន្នន័យ, cron job, ស្រទាប់ REST, ការអ៊ិនគ្រីបព័ត៌មានសម្ងាត់ និង

  cursor នឹងផ្លាស់ទីរំលងពួកវាជាអចិន្ត្រៃយ៍។
- គោលដៅដែលទទួល URL ផ្តល់ដោយអ្នកប្រើ ត្រូវតែ validate វាតាមរយៈ
  `parseAndValidateWebhookUrl` (`src/shared/network/outboundUrlGuardPolicy.ts`) មុនពេល fetch
  ដូចគ្នានឹងរបៀបដែល webhook ធ្វើ។ BigQuery មិនត្រូវការវាទេ៖ host របស់វាជាតម្លៃថេរ។
