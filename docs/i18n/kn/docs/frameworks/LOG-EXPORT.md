OmniRoute ಕರೆ ಲಾಗ್ಗಳನ್ನು ಬಾಹ್ಯ ಅನಾಲಿಟಿಕ್ಸ್ ಸ್ಟೋರ್ಗೆ ನಿರಂತರವಾಗಿ, ಇನ್ಕ್ರಿಮೆಂಟಲ್ ಆಗಿ ರಫ್ತು ಮಾಡುವುದು.

Logs ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಟ್ಯಾಬ್ ವಿನಂತಿ ಇತಿಹಾಸವನ್ನು SQLite (`call_logs`) ನಲ್ಲಿ ಇರಿಸುತ್ತದೆ; ಇದು
ರೊಟೇಶನ್ ಮತ್ತು ರಿಟೆನ್ಶನ್ನಿಂದ ಮಿತಿಗೊಳಿಸಲ್ಪಟ್ಟಿದೆ. ಲಾಗ್ ರಫ್ತು ಅದೇ ದಾಖಲೆಗಳ ಸಮೂಹವನ್ನು ವೇಳಾಪಟ್ಟಿಯಂತೆ ಹೊರಗೆ ಕಳುಹಿಸುತ್ತದೆ, ಇದರಿಂದ ಅವು
ಸ್ಥಳೀಯ ಡೇಟಾಬೇಸ್ಗಿಂತ ಹೆಚ್ಚು ಕಾಲ ಉಳಿಯಬಹುದು ಮತ್ತು ಇತರ ಡೇಟಾದೊಂದಿಗೆ ಜೋಡಿಸಬಹುದು. BigQuery ಮೊದಲ ಗಮ್ಯಸ್ಥಾನವಾಗಿದೆ;
ಪೈಪ್ಲೈನ್ ಒಂದು ರಿಜಿಸ್ಟ್ರಿಯಾಗಿರುವುದರಿಂದ, ಹೆಚ್ಚಿನ ಗಮ್ಯಸ್ಥಾನಗಳನ್ನು ಹೆಚ್ಚುವರಿಯಾಗಿ ಸೇರಿಸಬಹುದು.

## 1. ಇದು ಹೇಗೆ ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತದೆ

```
ಸರ್ವರ್ (ಕಾನ್ಫಿಗ್ ಡೀಕ್ರಿಪ್ಟ್ + ಮೌಲ್ಯೀಕರಣ, ಕರ್ಸರ್ ಸಮನ್ವಯ)
  → IPC ಪ್ರಾರಂಭ → ಪ್ರತ್ಯೇಕಿಸಿದ exportChild OS ಪ್ರಕ್ರಿಯೆ
    → ಓದಲು-ಮಾತ್ರ storage.sqlite → ಹಂಚಿದ call-log ಕ್ವೆರಿ/ಮ್ಯಾಪಿಂಗ್
      → ಅಸಿಂಕ್ ಆರ್ಟಿಫ್ಯಾಕ್ಟ್ ಹೈಡ್ರೇಶನ್ → ಗಮ್ಯಸ್ಥಾನದ prepare()/send()
        → ಬ್ಯಾಚ್ IPC → ಸರ್ವರ್ ಕರ್ಸರ್ ಉಳಿಸುತ್ತದೆ → ದೃಢೀಕರಣ IPC
          → ಮುಂದಿನ ಬ್ಯಾಚ್; ಪೂರ್ಣಗೊಂಡ IPC → ಸರ್ವರ್ ಯಶಸ್ಸನ್ನು ದಾಖಲಿಸುತ್ತದೆ
```

- **ವೇಳಾಪಟ್ಟಿ** — ಒಂದು `JobRegistry` cron ಕೆಲಸ, `log_export`, ಡೀಫಾಲ್ಟ್ ಆಗಿ `0 * * * *` (ಪ್ರತಿ ಗಂಟೆ,
  UTC). `src/lib/initCloudSync.ts` ನಲ್ಲಿ ನೋಂದಾಯಿಸಲಾಗಿದೆ; `OMNIROUTE_LOG_EXPORT_CRON` ಮೂಲಕ ಅತಿಕ್ರಮಿಸಬಹುದು.
  ಪ್ರತಿ ಟಿಕ್ನಲ್ಲಿ ಪ್ರತಿ **ಸಕ್ರಿಯಗೊಳಿಸಿದ** ಗಮ್ಯಸ್ಥಾನವನ್ನು ಅನುಕ್ರಮವಾಗಿ ಸಂಪೂರ್ಣವಾಗಿ ಪ್ರಕ್ರಿಯೆಗೊಳಿಸಲಾಗುತ್ತದೆ.
- **ಕರ್ಸರ್** — SQLite ನ ಅಪ್ರತ್ಯಕ್ಷ `call_logs.rowid`, ಪ್ರತಿ ಗಮ್ಯಸ್ಥಾನಕ್ಕೆ
  `log_export_destinations.cursor_row_id` ನಲ್ಲಿ ಉಳಿಸಲಾಗುತ್ತದೆ. `timestamp` ಅನ್ನು ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ ಕರ್ಸರ್ ಆಗಿ ಬಳಸುವುದಿಲ್ಲ:
  ಕರೆ ಮಾಡುವವರು ತಮ್ಮದೇ ಮೌಲ್ಯವನ್ನು ಒದಗಿಸಬಹುದು, ಆದ್ದರಿಂದ ನಿಧಾನವಾದ ವಿನಂತಿಯು ನಂತರ ಪ್ರಾರಂಭವಾದ ವೇಗದ ವಿನಂತಿಯ ಬಳಿಕ
  ಬರೆಯಲ್ಪಡಬಹುದು ಮತ್ತು timestamp ಕರ್ಸರ್ ಅದನ್ನು ಬಿಟ್ಟುಬಿಡುತ್ತದೆ.
- **ಬ್ಯಾಚಿಂಗ್** — ಪ್ರತಿ ವಿನಂತಿಗೆ `batch_size` ಸಾಲುಗಳು (ಡೀಫಾಲ್ಟ್ 500), ಪ್ರತಿ ರನ್ಗೆ
  `max_rows_per_run` ಸಾಲುಗಳು (ಡೀಫಾಲ್ಟ್ 10000); ಇದರಿಂದ ದೊಡ್ಡ ಬಾಕಿ ಸಂಗ್ರಹವು ಒಂದೇ ರನ್ ಅನ್ನು ತಡೆಯುವ ಬದಲು
  ಹಲವು ಟಿಕ್ಗಳಲ್ಲಿ ತೆರವುಗೊಳ್ಳುತ್ತದೆ.
- **ತಲುಪಿಸುವಿಕೆ** — `send()` ಪೂರ್ಣಗೊಂಡ ನಂತರ ಮಾತ್ರ ಕರ್ಸರ್ ಮುಂದುವರಿಯುತ್ತದೆ. ವಿಫಲವಾದ ಬ್ಯಾಚ್ ಕರ್ಸರ್ ಅನ್ನು
  ಇದ್ದಲ್ಲಿಯೇ ಬಿಡುತ್ತದೆ, ಆದ್ದರಿಂದ ಮುಂದಿನ ರನ್ನಲ್ಲಿ ಅದೇ ಸಾಲುಗಳನ್ನು ಮರುಪ್ರಯತ್ನಿಸಲಾಗುತ್ತದೆ. ಖಾತರಿಯು
  ಕನಿಷ್ಠ-ಒಮ್ಮೆ ತಲುಪಿಸುವಿಕೆ ಮತ್ತು ಗಮ್ಯಸ್ಥಾನ-ಬದಿಯ ನಕಲು-ನಿವಾರಣೆಯಾಗಿದೆ, ನಿಜವಾದ ನಿಖರವಾಗಿ-ಒಮ್ಮೆ ಅಲ್ಲ: BigQuery ಪ್ರತಿ
  ಸಾಲಿಗೆ call-log id ಮೂಲಕ ಕೀ ನೀಡುತ್ತದೆ ಮತ್ತು ತನ್ನದೇ ನಕಲು-ನಿವಾರಣಾ ವಿಂಡೋ ಒಳಗೆ ಸಾಧ್ಯವಾದಷ್ಟು ಉತ್ತಮವಾಗಿ ಅದನ್ನು ಪಾಲಿಸುತ್ತದೆ.
- **ಅತಿಕ್ರಮಣ ರಕ್ಷಣೆ** — cron ಟಿಕ್ ಮತ್ತು `POST .../run` ಒಟ್ಟಿಗೆ ಚಾಲನೆಯಾಗಬಹುದು. ಈಗಾಗಲೇ
  ಪ್ರಕ್ರಿಯೆಗೊಳ್ಳುತ್ತಿರುವ ಗಮ್ಯಸ್ಥಾನವನ್ನು ಎರಡು ಬಾರಿ ಪ್ರಕ್ರಿಯೆಗೊಳಿಸುವ ಬದಲು ಬಿಟ್ಟುಬಿಡಲಾಗುತ್ತದೆ (ರನ್ ಫಲಿತಾಂಶದಲ್ಲಿ `skipped: true`),
  ಆದ್ದರಿಂದ ಸಮಕಾಲೀನ ರನ್ ಬ್ಯಾಚ್ ಅನ್ನು ಮರುಕಳುಹಿಸಲು ಅಥವಾ ಕರ್ಸರ್ ಅನ್ನು ಹಿಂದಕ್ಕೆ ಬರೆಯಲು ಸಾಧ್ಯವಿಲ್ಲ.
- **ಪರ್ಜ್ ಮರುಪಡೆಯುವಿಕೆ** — `cursor_row_id` ಕೊನೆಗೆ `MAX(rowid)` ಗಿಂತ ಹೆಚ್ಚಾದರೆ (ಸಂಪೂರ್ಣ ಟೇಬಲ್ ಅನ್ನು
  ಪರ್ಜ್ ಮಾಡಿ rowid ಗಳು ಮರುಪ್ರಾರಂಭಗೊಂಡಿದ್ದರೆ), ರನ್ನರ್ ಶಾಶ್ವತವಾಗಿ ಯಾವುದನ್ನೂ ಕಾಣದಂತಾಗುವ ಬದಲು 0 ಗೆ ಹಿಂದಿರುಗುತ್ತದೆ.

### ಪ್ರತ್ಯೇಕಿಸಿದ ರನ್ನರ್ ಮತ್ತು ಮಿತಿಗಳು

Node ನಲ್ಲಿನ ಪ್ರತಿ ಗಮ್ಯಸ್ಥಾನ ರನ್ ಪ್ರತ್ಯೇಕವಾದ, ಅಲ್ಪಕಾಲಿಕ OS ಚೈಲ್ಡ್ ಪ್ರಕ್ರಿಯೆಯನ್ನು (`child_process`
ಜೊತೆಗೆ IPC, `worker_threads` ಅಲ್ಲ) ಪ್ರಾರಂಭಿಸುತ್ತದೆ. ಬಾಡಿ ಓದುವಿಕೆ, ಪೇಲೋಡ್ JSON ಪಾರ್ಸಿಂಗ್/ಸೀರಿಯಲೈಸೇಶನ್, ಗಮ್ಯಸ್ಥಾನದ
`prepare()` ಮತ್ತು ಗಮ್ಯಸ್ಥಾನದ ನೆಟ್ವರ್ಕ್ I/O ಎಲ್ಲವೂ ಅಲ್ಲಿಯೇ ನಡೆಯುತ್ತವೆ, ಸರ್ವರ್ನ event loop ನಲ್ಲಿ ಅಲ್ಲ.
IPC ಮೂಲಕ ಕಾನ್ಫಿಗರೇಶನ್ ಮತ್ತು ಸಣ್ಣ ಪ್ರಗತಿ ಸಂದೇಶಗಳು ಮಾತ್ರ ಹಾದುಹೋಗುತ್ತವೆ; ರಫ್ತು ಮಾಡಿದ ದಾಖಲೆಗಳು ಎಂದಿಗೂ
ಸರ್ವರ್ಗೆ ಹಿಂದಿರುಗುವುದಿಲ್ಲ. cron ಕೆಲಸ ಮತ್ತು Run now ರೂಟ್ ಒಂದೇ ಸಾರ್ವಜನಿಕ ಫಲಿತಾಂಶ ಮತ್ತು ಅತಿಕ್ರಮಣ ರಕ್ಷಣೆಯನ್ನು ಉಳಿಸಿಕೊಳ್ಳುತ್ತವೆ.

ಚೈಲ್ಡ್, ಸರ್ವರ್ ಪರಿಹರಿಸಿದ `DATA_DIR/storage.sqlite` ಅನ್ನು `node:sqlite` ಬಳಸಿ ಓದಲು-ಮಾತ್ರವಾಗಿ ತೆರೆಯುತ್ತದೆ,
`busy_timeout=5000` ಮತ್ತು `query_only=ON` ಜೊತೆಗೆ. ಇದು ಯಾವುದೇ DB singleton ಅನ್ನು ಆಮದು ಮಾಡುವುದಿಲ್ಲ ಮತ್ತು ಯಾವುದೇ
ಮೈಗ್ರೇಶನ್ಗಳು, ಬ್ಯಾಕಪ್ಗಳು ಅಥವಾ SQLite ಅಪ್ಡೇಟ್ಗಳನ್ನು ಮಾಡುವುದಿಲ್ಲ. ಕಾಣೆಯಾದ/ದೋಷಪೂರಿತ ಆರ್ಟಿಫ್ಯಾಕ್ಟ್ ಲೆಕ್ಕಪತ್ರ ನಿರ್ವಹಣೆ
(ದೋಷಪೂರಿತ-ಆರ್ಟಿಫ್ಯಾಕ್ಟ್ UPDATE ಸೇರಿದಂತೆ) ಡ್ಯಾಶ್ಬೋರ್ಡ್ ವಿವರ ಮಾರ್ಗದಲ್ಲಿ ಮಾತ್ರ ಉಳಿಯುತ್ತದೆ. ಎರಡೂ ಮಾರ್ಗಗಳು ಶುದ್ಧ
ವಿವರ ರಿಸಲ್ವರ್ ಅನ್ನು ಹಂಚಿಕೊಳ್ಳುತ್ತವೆ; ರಫ್ತು ಅಸಿಂಕ್ರೋನಸ್ ಫೈಲ್ಸಿಸ್ಟಮ್ ಓದುವಿಕೆ ಮತ್ತು ಅದೇ ಆರ್ಟಿಫ್ಯಾಕ್ಟ್ → ಲೆಗಸಿ
ಇನ್ಲೈನ್ → ಲೆಗಸಿ ಡಿಸ್ಕ್ → ಯಾವುದೂ ಇಲ್ಲ ಎಂಬ ಪರಿಹಾರ ಕ್ರಮವನ್ನು ಬಳಸುತ್ತದೆ. ಚೈಲ್ಡ್ ತನ್ನ ರೀಡರ್ ಅನ್ನು ತೆರೆಯುವಾಗ
ರನ್ ಗರಿಷ್ಠ ಸೇರಿಸುವಿಕೆ rowid ನ ಸ್ನ್ಯಾಪ್ಶಾಟ್ ತೆಗೆದುಕೊಳ್ಳುತ್ತದೆ; ನಂತರದ ಸೇರಿಸುವಿಕೆಗಳು ಮುಂದಿನ ರನ್ಗಾಗಿ ಕಾಯುತ್ತವೆ. ಇದು
ಸೇರಿಸುವಿಕೆಯ ಗಡಿಯೇ ಹೊರತು ದೀರ್ಘಕಾಲದ SQLite ವಹಿವಾಟು ಅಲ್ಲ: ನೆಟ್ವರ್ಕ್ ಕಾಯುವಿಕೆಗಳ ಸಮಯದಲ್ಲಿ WAL ರೈಟರ್ಗಳು ಮತ್ತು
ಚೆಕ್ಪಾಯಿಂಟ್ಗಳು ಮುಕ್ತವಾಗಿರುತ್ತವೆ. ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಸಾಲುಗಳ ಅಪ್ಡೇಟ್ಗಳು/ಅಳಿಸುವಿಕೆಗಳು ಈ ಗಡಿಯಿಂದ ಸ್ಥಗಿತಗೊಳ್ಳುವುದಿಲ್ಲ.

ಸ್ವೀಕರಿಸಲಾದ ಪ್ರತಿ ಬ್ಯಾಚ್ ನಂತರ, ಚೈಲ್ಡ್ ದೃಢೀಕರಣಕ್ಕಾಗಿ ಕಾಯುತ್ತದೆ. ಸರ್ವರ್ ಮೊದಲು
`advanceLogExportCursor` ಮೂಲಕ ಕರ್ಸರ್ ಅನ್ನು ಉಳಿಸಿ, ನಂತರ `ack` ಕಳುಹಿಸುತ್ತದೆ; ಅದಕ್ಕೂ ಮೊದಲು ಯಾವುದೇ ಮುಂದಿನ ಬ್ಯಾಚ್
ಪ್ರಾರಂಭವಾಗುವುದಿಲ್ಲ. ಕಳುಹಿಸುವಿಕೆಯ ವೈಫಲ್ಯ, ಕ್ರ್ಯಾಶ್ ಅಥವಾ ಸಮಯಮೀರಿಕೆಯು ಆ ಬ್ಯಾಚ್ ಅನ್ನು ಮುಂದುವರಿಸದೆ ವೈಫಲ್ಯವನ್ನು ದಾಖಲಿಸುತ್ತದೆ.
ಈ ಹಿಂದೆ ದೃಢೀಕರಿಸಿದ ಬ್ಯಾಚ್ಗಳು ಕಮಿಟ್ ಆಗಿಯೇ ಉಳಿಯುತ್ತವೆ; ದೃಢೀಕರಿಸದ ಒಂದೇ ಬ್ಯಾಚ್ ಅನ್ನು ಗರಿಷ್ಠವಾಗಿ ಮರುಕಳುಹಿಸಬಹುದು.
`done` ಮತ್ತು ದೋಷವಿಲ್ಲದ ಚೈಲ್ಡ್ ನಿರ್ಗಮನದ ನಂತರ ಮಾತ್ರ ಯಶಸ್ಸನ್ನು ದಾಖಲಿಸಲಾಗುತ್ತದೆ. ವೈಫಲ್ಯಗಳು ಚೈಲ್ಡ್ ಅನ್ನು
SIGTERM ಮೂಲಕ ಅಂತ್ಯಗೊಳಿಸುತ್ತವೆ, 500 ms ನಂತರ SIGKILL ಗೆ ಹೆಚ್ಚಿಸುತ್ತವೆ ಮತ್ತು ರನ್ನರ್ ಪ್ರಕ್ರಿಯೆ ಮುಚ್ಚುವವರೆಗೆ ಕಾಯುತ್ತದೆ.

| ಪರಿಸರ ವೇರಿಯಬಲ್                                | ಡೀಫಾಲ್ಟ್ | ಉದ್ದೇಶ                            |
| --------------------------------------------- | -------- | --------------------------------- |
| `OMNIROUTE_LOG_EXPORT_RUN_TIMEOUT_MS`         | 900000   | ಪ್ರತಿ ಗಮ್ಯಸ್ಥಾನದ ವಾಲ್-ಕ್ಲಾಕ್ ಮಿತಿ |
| `OMNIROUTE_LOG_EXPORT_CHILD_MAX_OLD_SPACE_MB` | 1024     | MB ನಲ್ಲಿ ಚೈಲ್ಡ್ V8 old-space ಮಿತಿ |

ಅಮಾನ್ಯ/ಧನಾತ್ಮಕವಲ್ಲದ/ಪೂರ್ಣಾಂಕವಲ್ಲದ ಮೌಲ್ಯಗಳು ಡೀಫಾಲ್ಟ್ಗಳನ್ನು ಬಳಸುತ್ತವೆ. heap ಸೆಟ್ಟಿಂಗ್ ಒಟ್ಟು
RSS ಮಿತಿಯಲ್ಲ; ಬಹಳ ದೊಡ್ಡ ಬ್ಯಾಚ್ಗಳು ಇನ್ನೂ ಚೈಲ್ಡ್ ಮೆಮೊರಿಯನ್ನು ಖಾಲಿ ಮಾಡಿ ರನ್ ಅನ್ನು ಸುರಕ್ಷಿತವಾಗಿ ವಿಫಲಗೊಳಿಸಬಹುದು.
ಬಾಡಿಗಳು ಸಕ್ರಿಯವಾಗಿರುವ 512 KiB ಆರ್ಟಿಫ್ಯಾಕ್ಟ್ಗಳ ಡೀಫಾಲ್ಟ್ 500-ಸಾಲಿನ ಬ್ಯಾಚ್ಗೆ, BigQuery ನ ಬೈಟ್-ಚಂಕ್ ಮಾಡಿದ
JSON ಸೀರಿಯಲೈಸೇಶನ್ ಸೇರಿದಂತೆ, 1024 MB ಡೀಫಾಲ್ಟ್ ಹೆಚ್ಚುವರಿ ಅವಕಾಶವನ್ನು ಬಿಡುತ್ತದೆ. ಇದು
10000-ಸಾಲಿನ ಬಾಡಿಗಳ ಬ್ಯಾಚ್ ಅನ್ನು ಸುರಕ್ಷಿತಗೊಳಿಸುವುದಿಲ್ಲ. V8 heap ಖಾಲಿಯಾಗುವಿಕೆಯು ಕ್ರಮ ಕೈಗೊಳ್ಳಬಹುದಾದ ವೈಫಲ್ಯವನ್ನು ದಾಖಲಿಸುತ್ತದೆ:
ಬ್ಯಾಚ್ ಗಾತ್ರವನ್ನು ಕಡಿಮೆ ಮಾಡಿ ಅಥವಾ `OMNIROUTE_LOG_EXPORT_CHILD_MAX_OLD_SPACE_MB` ಹೆಚ್ಚಿಸಿ; ಕರ್ಸರ್ ಕೊನೆಯ
ದೃಢೀಕರಿಸಿದ ಬ್ಯಾಚ್ನಲ್ಲಿಯೇ ಉಳಿಯುತ್ತದೆ. ಐತಿಹಾಸಿಕ ಇನ್ಲೈನ್/ಡಿಸ್ಕ್ ಬಾಡಿಗಳು ಆಧುನಿಕ ಆರ್ಟಿಫ್ಯಾಕ್ಟ್ ಮಿತಿಗೆ ಒಳಪಡುವುದಿಲ್ಲ.
ಆಪರೇಟರ್ಗಳು RSS ಗಾಗಿ ಪ್ರತ್ಯೇಕವಾಗಿ ಸಂಪನ್ಮೂಲ ಯೋಜಿಸಬೇಕು, ವಿಶೇಷವಾಗಿ ಮೆಮೊರಿ-ಮಿತಿಯ ಕಂಟೇನರ್ಗಳ ಒಳಗೆ.

ಚೈಲ್ಡ್ ಪರಿಹರಿಸಿದ `DATA_DIR`, `NODE_ENV`, ಸ್ಪಷ್ಟ `TZ` (ಲೆಗಸಿ ಫೈಲ್ಹೆಸರಿನ
ಸ್ಥಳೀಯ-ಸಮಯ ಪರಿಹಾರ), ಲಭ್ಯವಿದ್ದಾಗ `ELECTRON_RUN_AS_NODE` ಮತ್ತು ಕೆಳಗಿನ ಔಟ್ಬೌಂಡ್ ಇನ್ಪುಟ್ಗಳನ್ನು ಮಾತ್ರ ಆನುವಂಶಿಕವಾಗಿ ಪಡೆಯುತ್ತದೆ:
`HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, `NO_PROXY` (ಮತ್ತು ಅವುಗಳ lowercase ರೂಪಗಳು),
`OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS`, `NODE_EXTRA_CA_CERTS`, `SSL_CERT_FILE`, `SSL_CERT_DIR`.
ಜಾಗತಿಕ Undici dispatcher, `NO_PROXY` ಸೇರಿದಂತೆ, ಸರ್ವರ್ನ ಶುದ್ಧ environment-proxy ಪರಿಹಾರ ಮತ್ತು local-host
ಬೈಪಾಸ್ ನಿಯಮಗಳನ್ನು ಹಂಚಿಕೊಳ್ಳುತ್ತದೆ; ಅದು `proxyFetch.ts` ಅಥವಾ ಅದರ DB/feature flags ಅನ್ನು ಆಮದು ಮಾಡುವುದಿಲ್ಲ.
ಫಾರ್ವರ್ಡ್ ಮಾಡಿದ ಔಟ್ಪುಟ್ ಮತ್ತು ದಾಖಲಿಸಿದ ದೋಷಗಳಿಂದ ಪ್ರಾಕ್ಸಿ ರುಜುವಾತುಗಳನ್ನು ಮರೆಮಾಡಲಾಗುತ್ತದೆ. ಗಮ್ಯಸ್ಥಾನದ ರುಜುವಾತುಗಳು
ಒಂದೇ ಪ್ರಾರಂಭ IPC ಸಂದೇಶದಲ್ಲಿ ಮಾತ್ರ ಸಾಗುತ್ತವೆ, argv ಅಥವಾ environment ನಲ್ಲಿ ಎಂದಿಗೂ ಅಲ್ಲ; ಔಟ್ಪುಟ್/ದೋಷ ಫಾರ್ವರ್ಡಿಂಗ್ಗೆ
ಪೂರ್ವಪ್ರತ್ಯಯ ಸೇರಿಸಿ ಸ್ವಚ್ಛಗೊಳಿಸಲಾಗುತ್ತದೆ. ಪ್ರತಿ cron ರನ್ನಲ್ಲಿ Node ನ SQLite ಎಚ್ಚರಿಕೆಯನ್ನು ಪುನರಾವರ್ತಿಸುವುದನ್ನು ತಪ್ಪಿಸಲು
ಚೈಲ್ಡ್ exec arguments ನಲ್ಲಿ `ExperimentalWarning` ಅನ್ನು ಮಾತ್ರ ನಿಷ್ಕ್ರಿಯಗೊಳಿಸಲಾಗಿದೆ; ಇತರ ಎಚ್ಚರಿಕೆ ಪ್ರಕಾರಗಳು ಗೋಚರಿಸುತ್ತಲೇ ಇರುತ್ತವೆ.

ಗಮ್ಯಸ್ಥಾನ ಮಾಡ್ಯೂಲ್ಗಳು Next.js/server-only ಅವಲಂಬನೆಗಳಿಲ್ಲದೆ ಆಮದು ಮಾಡಬಹುದಾಗಿರಬೇಕು. ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ
BigQuery ಅನುಷ್ಠಾನವು ಈಗಾಗಲೇ ಆ ಒಪ್ಪಂದವನ್ನು ಪೂರೈಸುತ್ತದೆ. ಪ್ರವೇಶ-ಟೋಕನ್ ಕ್ಯಾಶ್ಗಳು ಉಪ ಪ್ರಕ್ರಿಯೆಯ
ಚಾಲನೆಯ ಅವಧಿಯವರೆಗೆ ಮಾತ್ರ ಇರುತ್ತವೆ, ಚಾಲನೆಗಳ ನಡುವೆ ಅಲ್ಲ. Node ಬೆಂಬಲಿತ ರನ್ಟೈಮ್ ಆಗಿದೆ (`package.json` ಎಂಜಿನ್ಗಳು), ಆದರೆ README ಯ Bun
ಅನುಸ್ಥಾಪನಾ ವಿಭಾಗ ಮತ್ತು `Dockerfile.bun` ಸಹ `bun:sqlite` (`src/lib/db/core.ts` / ಅಡಾಪ್ಟರ್ಗಳು) ಬಳಸುವ
ಉತ್ಪಾದನಾ ಹೊಂದಾಣಿಕೆ ಮಾರ್ಗವನ್ನು ಪ್ರಕಟಿಸುತ್ತವೆ. ಆದ್ದರಿಂದ Bun ಅಡಿಯಲ್ಲಿ, ರಫ್ತುಗಳು ಹಿಂದಿನ
ಪ್ರಕ್ರಿಯೆಯೊಳಗಿನ ಮಾರ್ಗವನ್ನು ಉಳಿಸಿಕೊಳ್ಳುತ್ತವೆ ಮತ್ತು ಒಂದು-ಬಾರಿಯ ಎಚ್ಚರಿಕೆಯನ್ನು ಹೊರಸೂಸುತ್ತವೆ: ಉಪ ಪ್ರಕ್ರಿಯೆಯ ಹೀಪ್/ಕಾಲಮಿತಿ ಪ್ರತ್ಯೇಕತೆ ಲಭ್ಯವಿಲ್ಲ.
ಈವೆಂಟ್-ಲೂಪ್ ಮತ್ತು OOM ಪ್ರತ್ಯೇಕತೆಗಾಗಿ Node ಬಳಸಿ; ಇಲ್ಲಿ Bun ಅನ್ನು ಅಭಿವೃದ್ಧಿಗೆ ಮಾತ್ರ ಸೀಮಿತವೆಂದು ಪರಿಗಣಿಸಲಾಗುವುದಿಲ್ಲ.

`includeBodies` ಸಕ್ರಿಯಗೊಳಿಸಿದಾಗ, ಗಂಟೆಗೊಮ್ಮೆ ಪೇಲೋಡ್ ಬಾಕಿ ಸಂಗ್ರಹಿಸುವ ಬದಲು
`OMNIROUTE_LOG_EXPORT_CRON="*/5 * * * *"` ನಂತಹ ನಿಮಿಷ-ಮಟ್ಟದ ವೇಳಾಪಟ್ಟಿಗೆ ಆದ್ಯತೆ ನೀಡಿ.
ಬ್ಯಾಚ್ ಮತ್ತು ಸಾಲಿನ ಮಿತಿಗಳು ಇನ್ನೂ ಪ್ರತಿ ಚಾಲನೆಯನ್ನು ನಿಯಂತ್ರಿಸುತ್ತವೆ. ಪ್ರತಿ ಚಾಲನೆಯಲ್ಲಿ ಪ್ರತಿ ಗಮ್ಯಸ್ಥಾನಕ್ಕೂ ಪ್ರಕ್ರಿಯೆ ಪ್ರಾರಂಭಿಸುವ ವೆಚ್ಚವನ್ನು ಭರಿಸಬೇಕಾಗುತ್ತದೆ;
ಇದು ಒಟ್ಟು CPU ಬಳಕೆಯನ್ನು ಕಡಿಮೆ ಮಾಡುವುದಕ್ಕಾಗಿ ಅಲ್ಲ, ಬದಲಿಗೆ ಸರ್ವರ್ ಈವೆಂಟ್-ಲೂಪ್ ಪ್ರತ್ಯೇಕತೆಗಾಗಿ ಸಣ್ಣ ಪ್ರಾರಂಭಿಕ ವೆಚ್ಚವನ್ನು ವಿನಿಮಯ ಮಾಡಿಕೊಳ್ಳುತ್ತದೆ.

### ಪೇಲೋಡ್ಗಳು (ಪ್ರಾಂಪ್ಟ್ಗಳು ಮತ್ತು ಪೂರ್ಣಗೊಳಿಸುವಿಕೆಗಳು)

ಪೂರ್ವನಿಯೋಜಿತವಾಗಿ, ರಫ್ತು Logs **ಪಟ್ಟಿ** ತೋರಿಸುವ ಸಾರಾಂಶ ಕ್ಷೇತ್ರಗಳನ್ನು ಮಾತ್ರ ಒಳಗೊಂಡಿರುತ್ತದೆ.
**ಪ್ರಾಂಪ್ಟ್ಗಳು ಮತ್ತು ಪ್ರತಿಕ್ರಿಯೆಗಳನ್ನು ರಫ್ತುಮಾಡಿ** (`includeBodies`) ಅನ್ನು ಸಕ್ರಿಯಗೊಳಿಸಿದರೆ, ಪ್ರತಿ ಕರೆಗಾಗಿ Logs **ವಿವರ**
ಫಲಕ ತೋರಿಸುವ ಮಾಹಿತಿಯನ್ನೂ ಹೆಚ್ಚುವರಿಯಾಗಿ ಕಳುಹಿಸುತ್ತದೆ:

| ಕ್ಷೇತ್ರ                          | ಅದು ಒಳಗೊಂಡಿರುವುದು                                            |
| -------------------------------- | ------------------------------------------------------------ |
| `request_body` / `response_body` | ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಪ್ರದರ್ಶಿಸುವ ರೀತಿಯಲ್ಲೇ ಕರೆ ಪೇಲೋಡ್ಗಳು             |
| `pipeline_route_decision`        | ರೌಟರ್ ಆಯ್ಕೆಮಾಡಿದ ಗುರಿ ಮತ್ತು ಮಾಡೆಲ್                           |
| `pipeline_client_request`        | ಕ್ಲೈಂಟ್ ಕಳುಹಿಸಿದಂತೆಯೇ ಇರುವ ಕಚ್ಚಾ ವಿನಂತಿ                      |
| `pipeline_openai_request`        | ಆಂತರಿಕ OpenAI ಸ್ವರೂಪಕ್ಕೆ ಅನುವಾದಿಸಿದ ನಂತರ                     |
| `pipeline_provider_request`      | ಪೂರೈಕೆದಾರರ ಉಪಭಾಷೆಯಲ್ಲಿ, ನಿಜವಾಗಿ ಅಪ್ಸ್ಟ್ರೀಮ್ಗೆ ಕಳುಹಿಸಿದಂತೆ    |
| `pipeline_provider_response`     | ಕಚ್ಚಾ ಅಪ್ಸ್ಟ್ರೀಮ್ ಪ್ರತಿಕ್ರಿಯೆ                                |
| `pipeline_client_response`       | ಕರೆ ಮಾಡಿದವರಿಗೆ ಹಿಂದಿರುಗಿಸಲಾದದ್ದು                             |
| `pipeline_error`                 | ವಿಫಲವಾದ ಕರೆಗೆ ಪೈಪ್ಲೈನ್-ಮಟ್ಟದ ದೋಷದ ವಿವರ                       |
| `bodies_truncated`               | ಮೇಲಿನ ಯಾವುದೇ ಕ್ಷೇತ್ರವು `maxBodyBytes` ಮಿತಿಯನ್ನು ತಲುಪಿದಾಗ ಸರಿ |

ಇದು ಪ್ರಾಂಪ್ಟ್ ವಿಷಯವಾಗಿರುವುದರಿಂದ, ಇದು **ಪೂರ್ವನಿಯೋಜಿತವಾಗಿ ನಿಷ್ಕ್ರಿಯವಾಗಿದೆ** ಮತ್ತು ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ ಪ್ರತಿ-ಗಮ್ಯಸ್ಥಾನದ ಆಯ್ಕೆಯಾಗಿದೆ.
ರಫ್ತು ಮತ್ತು `getCallLogById` ಒಂದೇ ವಿವರ ಪರಿಹಾರವನ್ನು ಹಂಚಿಕೊಳ್ಳುವುದರಿಂದ, ಡ್ಯಾಶ್ಬೋರ್ಡ್ ತೋರಿಸುವುದೇ
ಕಳುಹಿಸಲ್ಪಡುತ್ತದೆ: ಪೇಲೋಡ್ಗಳನ್ನು
ಬರೆಯುವಾಗಲೇ ಅವುಗಳ PII ಅನ್ನು ಸ್ವಚ್ಛಗೊಳಿಸಲಾಗುತ್ತದೆ ಮತ್ತು ರಹಸ್ಯಗಳನ್ನು ಮರೆಮಾಡಲಾಗುತ್ತದೆ; ಹಾಗೆಯೇ
`noLog` API ಕೀಲಿಯಿಂದ ಮಾಡಿದ ಕರೆಯು ಯಾವುದೇ ಪೇಲೋಡ್ ಅನ್ನು ಸಂಗ್ರಹಿಸುವುದಿಲ್ಲ, ಆದ್ದರಿಂದ ರಫ್ತುಮಾಡಲು ಏನೂ ಇರುವುದಿಲ್ಲ.

ಪೇಲೋಡ್ಗಳನ್ನು ಫೈಲ್ಸಿಸ್ಟಂ ಆರ್ಟಿಫ್ಯಾಕ್ಟ್ನಿಂದ ಪ್ರತಿ ಸಾಲಿಗೆ ಓದಲಾಗುತ್ತದೆ, ಆದ್ದರಿಂದ ಅವುಗಳನ್ನು ಕೇಳಿದ
ಗಮ್ಯಸ್ಥಾನಗಳಿಗಾಗಿ ಮಾತ್ರ ಹೈಡ್ರೇಷನ್ ನಡೆಯುತ್ತದೆ. ಆರ್ಟಿಫ್ಯಾಕ್ಟ್ ಕಾಣೆಯಾಗಿದ್ದರೆ ಅಥವಾ ದೋಷಪೂರಿತವಾಗಿದ್ದರೆ, ಬ್ಯಾಚ್ ವಿಫಲವಾಗಿ
ಕರ್ಸರ್ ಸಿಲುಕಿಕೊಳ್ಳುವಂತೆ ಮಾಡುವ ಬದಲು, ಅದರ ಸಾರಾಂಶವನ್ನು ಶೂನ್ಯ ಪೇಲೋಡ್ಗಳೊಂದಿಗೆ ರಫ್ತು ಮಾಡಲಾಗುತ್ತದೆ.

`maxBodyBytes` (ಪೂರ್ವನಿಯೋಜಿತ 262144) ಪ್ರತಿ ಕ್ಷೇತ್ರಕ್ಕೂ ಮಿತಿ ವಿಧಿಸುತ್ತದೆ. ಉದ್ದವಾದ ಪೇಲೋಡ್ಗಳನ್ನು **ಕೈಬಿಡುವ ಬದಲು
ಮೊಟಕುಗೊಳಿಸಲಾಗುತ್ತದೆ** — ತುಂಡರಿಸಿದ ಪ್ರಾಂಪ್ಟ್ ಸಹ "ಏನು ಕೇಳಲಾಗಿತ್ತು" ಎಂಬುದಕ್ಕೆ ಉತ್ತರಿಸುತ್ತದೆ — ಮತ್ತು ಸಾಲನ್ನು
`bodies_truncated` ಮೂಲಕ ಗುರುತಿಸಲಾಗುತ್ತದೆ. ತುಂಡು-ತುಂಡಾಗಿ ಸ್ಟ್ರೀಮ್ ಮಾಡಿದ ಡೆಲ್ಟಾಗಳನ್ನು ರಫ್ತು ಮಾಡುವುದಿಲ್ಲ; ಜೋಡಿಸಲಾದ ಪ್ರತಿಕ್ರಿಯೆಯು
ಈಗಾಗಲೇ `pipeline_provider_response` ಮತ್ತು `pipeline_client_response` ನಲ್ಲಿ ಇರುತ್ತದೆ.

## 3. REST API

ಎಲ್ಲಾ ರೂಟ್ಗಳು ನಿರ್ವಹಣಾ ದೃಢೀಕರಣವನ್ನು (`requireManagementAuth`) ಹೊಂದಿವೆ. ರಹಸ್ಯಗಳನ್ನು ಎಂದಿಗೂ ಹಿಂತಿರುಗಿಸಲಾಗುವುದಿಲ್ಲ:
ಸಂಗ್ರಹಿಸಲಾದ ರಹಸ್ಯವು ಅಕ್ಷರಶಃ `__stored__` ಆಗಿ ಮರಳುತ್ತದೆ ಮತ್ತು ಅಪ್ಡೇಟ್ ಮಾಡುವಾಗ ಆ ಮೌಲ್ಯವನ್ನೇ ಹಿಂದಕ್ಕೆ ಕಳುಹಿಸಿದರೆ
ಸಂಗ್ರಹಿಸಲಾದ ರುಜುವಾತು ಹಾಗೆಯೇ ಉಳಿಯುತ್ತದೆ.

ರಹಸ್ಯವನ್ನು ಘೋಷಿಸುವ ಪ್ರಕಾರದ ಗಮ್ಯಸ್ಥಾನವನ್ನು ರಚಿಸಲು ಅಥವಾ ಅಪ್ಡೇಟ್ ಮಾಡಲು **`STORAGE_ENCRYPTION_KEY`
ಅಗತ್ಯವಿದೆ**. ಅದು ಇಲ್ಲದಿದ್ದರೆ `encrypt()` ಯಾವುದೇ ಸೂಚನೆಯಿಲ್ಲದೆ ಇನ್ಪುಟ್ ಅನ್ನು ಹಾಗೆಯೇ ರವಾನಿಸುತ್ತದೆ, ಆದ್ದರಿಂದ ರುಜುವಾತನ್ನು
SQLite ನಲ್ಲಿ ಸರಳ ಪಠ್ಯವಾಗಿ ಇರಿಸುವ ಬದಲು ಬರೆಯುವಿಕೆಯನ್ನು 400 ದೋಷದೊಂದಿಗೆ ನಿರಾಕರಿಸಲಾಗುತ್ತದೆ (Telegram ವೆಬ್ಹುಕ್
ಅನ್ವಯಿಸುವ ಅದೇ ರಕ್ಷಣೆ).

## 4. BigQuery ಗಮ್ಯಸ್ಥಾನ

ಕಾನ್ಫಿಗ್ ಕೀಗಳು (`type: "bigquery"`):

| ಕೀ                   | ಟಿಪ್ಪಣಿಗಳು                                                                                       |
| -------------------- | ------------------------------------------------------------------------------------------------ |
| `projectId`          | ಡೇಟಾಸೆಟ್ ಅನ್ನು ಹೊಂದಿರುವ GCP ಪ್ರಾಜೆಕ್ಟ್                                                           |
| `datasetId`          | `[A-Za-z0-9_]+`                                                                                  |
| `tableId`            | `[A-Za-z0-9_]+`                                                                                  |
| `location`           | ಡೇಟಾಸೆಟ್ ರಚಿಸಬೇಕಾದಾಗ ಮಾತ್ರ ಬಳಸಲಾಗುತ್ತದೆ (ಡೀಫಾಲ್ಟ್ `EU`)                                          |
| `serviceAccountJson` | ಸರ್ವಿಸ್-ಅಕೌಂಟ್ ಕೀ. ರಹಸ್ಯ: ಸಂಗ್ರಹಿತ ಸ್ಥಿತಿಯಲ್ಲಿ ಎನ್ಕ್ರಿಪ್ಟ್ ಆಗಿರುತ್ತದೆ, ಎಂದಿಗೂ ಹಿಂತಿರುಗಿಸುವುದಿಲ್ಲ |
| `autoCreate`         | ಮೊದಲ ಎಕ್ಸ್ಪೋರ್ಟ್ನಲ್ಲಿ ಡೇಟಾಸೆಟ್ ಮತ್ತು ಟೇಬಲ್ ರಚಿಸಿ (ಡೀಫಾಲ್ಟ್ `true`)                               |

ಸರ್ವಿಸ್ ಅಕೌಂಟ್ಗೆ ಗುರಿ ಟೇಬಲ್ನಲ್ಲಿ `bigquery.tables.updateData` ಅಗತ್ಯವಿದೆ, ಜೊತೆಗೆ
`autoCreate` ಸಕ್ರಿಯವಾಗಿರುವಾಗ `bigquery.datasets.create` / `bigquery.tables.create` ಅಗತ್ಯವಿವೆ.

ಕಾನ್ಫಿಗರ್ ಮಾಡಲಾದ ಬ್ಯಾಚ್ ಒಂದು **ಕರ್ಸರ್** ಘಟಕವೇ ಹೊರತು HTTP ಘಟಕವಲ್ಲ: `send()` ಅದನ್ನು ಗರಿಷ್ಠ 500 ಸಾಲುಗಳ
insertAll ಕರೆಗಳಾಗಿ ವಿಭಜಿಸುತ್ತದೆ, ಆದ್ದರಿಂದ ದೊಡ್ಡ `batch_size` BigQuery ನ 10 MB ವಿನಂತಿ ಮಿತಿಯನ್ನು ಮೀರಿಸುವುದಿಲ್ಲ.
ತಾತ್ಕಾಲಿಕ ಸ್ಥಿತಿಗಳಲ್ಲಿ (408/429/500/502/503/504), ಅದೇ insertIds ಅನ್ನು ಮರುಬಳಸುತ್ತಾ ಎಕ್ಸ್ಪೊನೆನ್ಶಿಯಲ್
ಬ್ಯಾಕ್ಆಫ್ನೊಂದಿಗೆ ಗರಿಷ್ಠ ಮೂರು ಬಾರಿ ಮರುಪ್ರಯತ್ನಿಸಲಾಗುತ್ತದೆ; ದೃಢೀಕರಣ ಮತ್ತು ಸ್ಕೀಮಾ ವೈಫಲ್ಯಗಳು ರನ್ ಅನ್ನು
ವ್ಯರ್ಥಗೊಳಿಸುವ ಬದಲು ಮೊದಲ ಪ್ರಯತ್ನದಲ್ಲೇ ದೋಷವನ್ನು ಎಸೆಯುತ್ತವೆ.

ಕೆಲವೇ ಕ್ಷಣಗಳ ಹಿಂದೆ ರಚಿಸಲಾದ ಟೇಬಲ್ ಇನ್ನೂ ಸ್ಟ್ರೀಮಿಂಗ್ ಎಂಡ್ಪಾಯಿಂಟ್ಗೆ ಗೋಚರಿಸುವುದಿಲ್ಲ ಮತ್ತು ಅದು
ಕೆಲವು ಸೆಕೆಂಡುಗಳವರೆಗೆ 404 ಎಂದು ಉತ್ತರಿಸುತ್ತದೆ. ಆ 404 ಅನ್ನು ಮರುಪ್ರಯತ್ನಿಸಲಾಗುತ್ತದೆ, ಆದರೆ **ಈ ರನ್ ಟೇಬಲ್ ಅನ್ನು
ರಚಿಸಿದ್ದರೆ ಮಾತ್ರ** — ನಿಜವಾಗಿಯೂ ಕಾಣೆಯಾಗಿರುವ ಟೇಬಲ್ ತಕ್ಷಣವೇ ವಿಫಲವಾಗುತ್ತದೆ. ಇತ್ತೀಚೆಗೆ ಅಳಿಸಲಾದ ಹೆಸರಿನ
ಅಡಿಯಲ್ಲೇ ಟೇಬಲ್ ಅನ್ನು ಮರುರಚಿಸಿದರೆ, BigQuery ಹಲವು ನಿಮಿಷಗಳವರೆಗೆ ಸ್ಟ್ರೀಮಿಂಗ್ ಇನ್ಸರ್ಟ್ಗಳನ್ನು ನಿರಾಕರಿಸುತ್ತದೆ
ಎಂಬುದನ್ನು ಗಮನಿಸಿ; ಇದು ಅಳಿಸಿ-ನಂತರ-ಮರುರಚಿಸುವಿಕೆಯ ಗುಣಲಕ್ಷಣವಾಗಿದೆ, ಆದ್ದರಿಂದ ಟೇಬಲ್ ಅನ್ನು ಕೈಬಿಟ್ಟು ಮತ್ತೆ
ಸೇರಿಸುವ ಬದಲು ಹೊಸ ಟೇಬಲ್ ಹೆಸರನ್ನು ಬಳಸುವುದು ಉತ್ತಮ.

**ಭಾಗಶಃ ವೈಫಲ್ಯವು ಖಾಲಿಯಲ್ಲದ `insertErrors[]` ಜೊತೆಗೆ HTTP 200 ಆಗಿ ಬರುತ್ತದೆ.** ಅದನ್ನು ವೈಫಲ್ಯವೆಂದು
ಪರಿಗಣಿಸಿ ದೋಷವನ್ನು ಎಸೆಯಲಾಗುತ್ತದೆ; ಇದರಿಂದ BigQuery ಎಂದಿಗೂ ಸ್ವೀಕರಿಸದ ಸಾಲುಗಳನ್ನು ಮೀರಿ ಕರ್ಸರ್ ಮುಂದುವರಿಯುವುದನ್ನು
ತಡೆಯಲಾಗುತ್ತದೆ; `tests/unit/log-export-bigquery.test.ts` ಈ ವರ್ತನೆಯನ್ನು ಸ್ಥಿರಪಡಿಸುತ್ತದೆ.

ಟ್ರಾನ್ಸ್ಪೋರ್ಟ್ ಸರಳ REST ಆಗಿದೆ — ಸ್ವಯಂ-ಸಹಿ ಮಾಡಿದ RS256 ಅಸರ್ಷನ್ ಅನ್ನು
`https://oauth2.googleapis.com/token` ನಲ್ಲಿ ಆಕ್ಸೆಸ್ ಟೋಕನ್ಗೆ ವಿನಿಮಯ ಮಾಡಲಾಗುತ್ತದೆ, ನಂತರ ಸಾಲುಗಳು
`tabledata.insertAll` ಗೆ ಹೋಗುತ್ತವೆ. ಯಾವುದೇ Google SDK ಅನ್ನು ಸೇರಿಸಲಾಗುವುದಿಲ್ಲ. ಆಕ್ಸೆಸ್ ಟೋಕನ್ಗಳನ್ನು
ಪ್ರತಿ (ಸರ್ವಿಸ್ ಅಕೌಂಟ್, ಸ್ಕೋಪ್) ಗೆ ಪ್ರಕ್ರಿಯೆಯೊಳಗೆ ಕ್ಯಾಶ್ ಮಾಡಲಾಗುತ್ತದೆ.

ರಚಿಸಲಾದ ಟೇಬಲ್ನಲ್ಲಿ Logs-ಟ್ಯಾಬ್ನ ಪ್ರತಿ ಫೀಲ್ಡ್ಗೆ ಒಂದೊಂದು ಕಾಲಮ್ ಜೊತೆಗೆ `exported_at` ಇರುತ್ತದೆ ಮತ್ತು
ಕಾಲ್ ಲಾಗ್ಗಳನ್ನು ವಾಸ್ತವವಾಗಿ ಹೇಗೆ ಕ್ವೆರಿ ಮಾಡಲಾಗುತ್ತದೆ ಎಂಬುದಕ್ಕೆ ಅನುಗುಣವಾಗಿ ಅದನ್ನು ವಿನ್ಯಾಸಗೊಳಿಸಲಾಗಿದೆ:

- **`timestamp` ಆಧಾರಿತ ದಿನ-ವಿಭಜನೆ**, ಆದ್ದರಿಂದ ದಿನಾಂಕದಿಂದ ಮಿತಿಗೊಳಿಸಲಾದ ಕ್ವೆರಿ ಆ ದಿನಗಳನ್ನು ಮಾತ್ರ ಸ್ಕ್ಯಾನ್ ಮಾಡುತ್ತದೆ.
- **`api_key_name`, `provider`, `model`, `status` ಆಧಾರಿತ ಕ್ಲಸ್ಟರಿಂಗ್** (ಅದೇ ಕ್ರಮದಲ್ಲಿ), ಆದ್ದರಿಂದ
  ಅದನ್ನು ಯಾರು ಚಲಾಯಿಸಿದರು, ಅದು ಎಲ್ಲಿಗೆ ಹೋಯಿತು ಅಥವಾ ಅದು ವಿಫಲವಾಗಿದೆಯೇ ಎಂಬುದರ ಆಧಾರದ ಮೇಲೆ ಫಿಲ್ಟರ್ ಮಾಡುವುದರಿಂದ
  ಪ್ರತಿ ಪಾರ್ಟಿಷನ್ನೊಳಗಿನ ಬ್ಲಾಕ್ಗಳು ಕಡಿತಗೊಳ್ಳುತ್ತವೆ. BigQuery ಗರಿಷ್ಠ ನಾಲ್ಕು ಕ್ಲಸ್ಟರಿಂಗ್ ಕಾಲಮ್ಗಳನ್ನು
  ಅನುಮತಿಸುತ್ತದೆ ಮತ್ತು ಕ್ರಮವು ಮುಖ್ಯವಾಗಿದೆ: `api_key_name` ಮೇಲೆ ಮಾತ್ರ ಇರುವ ಫಿಲ್ಟರ್ ಬ್ಲಾಕ್ಗಳನ್ನು ಕಡಿತಗೊಳಿಸುತ್ತದೆ,
  ಆದರೆ `status` ಮೇಲೆ ಮಾತ್ರ ಇರುವ ಫಿಲ್ಟರ್ ಹಾಗೆ ಮಾಡುವುದಿಲ್ಲ.
- **`partitionExpirationDays` ಮೂಲಕ ಐಚ್ಛಿಕ ಪಾರ್ಟಿಷನ್ ಉಳಿಕೆ** (0 ಎಲ್ಲವನ್ನೂ ಉಳಿಸುತ್ತದೆ), ಟೇಬಲ್
  ರಚಿಸುವಾಗ ಅನ್ವಯಿಸಲಾಗುತ್ತದೆ.

ಎರಡೂ ಸೆಟ್ಟಿಂಗ್ಗಳು ರಚನೆಯ ಸಮಯದಲ್ಲಿ ಅನ್ವಯಿಸುತ್ತವೆ. ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಟೇಬಲ್ ತನ್ನಲ್ಲಿರುವ ವಿನ್ಯಾಸವನ್ನೇ ಉಳಿಸಿಕೊಳ್ಳುತ್ತದೆ, ಆದ್ದರಿಂದ
ಅವುಗಳನ್ನು ಅಳವಡಿಸಿಕೊಳ್ಳಲು ಬಯಸಿದರೆ ಗಮ್ಯಸ್ಥಾನವನ್ನು ಹೊಸ ಟೇಬಲ್ ID ಕಡೆಗೆ ನಿರ್ದೇಶಿಸಿ.

`tests/unit/log-export-bigquery.test.ts` ಮ್ಯಾಪರ್ ಮತ್ತು ಟೇಬಲ್ ಸ್ಕೀಮಾ ಒಂದಕ್ಕೊಂದು
ಹೊಂದಿಕೊಂಡೇ ಇರುವುದನ್ನು ದೃಢಪಡಿಸುತ್ತದೆ, ಹೀಗಾಗಿ ಹೊಸ ಕಾಲ್-ಲಾಗ್ ಕಾಲಮ್ ರಫ್ತಾಗುವಾಗ ಸದ್ದಿಲ್ಲದೆ ಕೈಬಿಡಲು ಸಾಧ್ಯವಿಲ್ಲ.

ಬ್ಯಾಚ್ಗಳನ್ನು ಸಾಲುಗಳ ಸಂಖ್ಯೆ ಮತ್ತು ಸೀರಿಯಲೈಸ್ ಮಾಡಿದ ಬೈಟ್ಗಳು **ಎರಡರ** ಆಧಾರದಲ್ಲಿಯೂ ಚಂಕ್ಗಳಾಗಿ ವಿಭಜಿಸಲಾಗುತ್ತದೆ. ಪೇಲೋಡ್ಗಳನ್ನು ರಫ್ತು ಮಾಡುವಾಗ
ಸಾಲುಗಳ ಸಂಖ್ಯೆ ಮಾತ್ರ ಸಾಕಾಗುವುದಿಲ್ಲ: ಪ್ರಾಂಪ್ಟ್ಗಳನ್ನು ಹೊಂದಿರುವ 500 ಸಾಲುಗಳು ಹತ್ತಾರು ಮೆಗಾಬೈಟ್ಗಳಷ್ಟಾಗಬಹುದು ಮತ್ತು 10 MB ಮೀರಿದ ವಿನಂತಿಯನ್ನು insertAll
ತಿರಸ್ಕರಿಸುತ್ತದೆ. 500 ಸಾಲುಗಳು ಅಥವಾ 9 MB—ಇವುಗಳಲ್ಲಿ ಯಾವುದು ಮೊದಲು ತಲುಪುತ್ತದೆಯೋ ಆಗ ಚಂಕ್ಗಳನ್ನು ಮುಚ್ಚಲಾಗುತ್ತದೆ.

## 5. ಗಮ್ಯಸ್ಥಾನವನ್ನು ಸೇರಿಸುವುದು

1. `LogExportDestinationType` ಅನ್ನು export ಮಾಡುವ `src/lib/logExport/destinations/<name>.ts` ಅನ್ನು ರಚಿಸಿ:
   UI ಗಾಗಿ Zod `configSchema`, `fields` ವಿವರಣಾ array, `secretFields`, ಮತ್ತು
   `test()` / `prepare()` / `send(records)` ಅನ್ನು ಹಿಂದಿರುಗಿಸುವ `createClient(config)`.
2. ಅದನ್ನು `src/lib/logExport/registry.ts` ನಲ್ಲಿರುವ `DESTINATIONS` array ಗೆ ಸೇರಿಸಿ.
3. `tests/unit/` ಅಡಿಯಲ್ಲಿ ಪರೀಕ್ಷೆಗಳನ್ನು ಬರೆಯಿರಿ.

ಬದಲಾವಣೆ ಇಷ್ಟೇ: persistence, cron job, REST layer, secret encryption ಮತ್ತು
dashboard form ಎಲ್ಲವೂ registry ಅನ್ನು ಓದುತ್ತವೆ.

ಹೊಸ ಗಮ್ಯಸ್ಥಾನಕ್ಕೆ ಎರಡು ನಿಯಮಗಳು:

- ಭಾಗಶಃ ವೈಫಲ್ಯ ಸಂಭವಿಸಿದಾಗ `send()` **throw ಮಾಡಲೇಬೇಕು**. resolve ಆಗುವುದು ಎಂದರೆ "ಗಮ್ಯಸ್ಥಾನವು ಈ rows ಅನ್ನು ಹೊಂದಿದೆ"
  ಎಂದರ್ಥ, ಮತ್ತು cursor ಅವುಗಳನ್ನು ಶಾಶ್ವತವಾಗಿ ದಾಟಿ ಮುಂದೆ ಸಾಗುತ್ತದೆ.
- ಬಳಕೆದಾರರು ಒದಗಿಸಿದ URL ಅನ್ನು ಸ್ವೀಕರಿಸುವ ಗಮ್ಯಸ್ಥಾನವು fetch ಮಾಡುವ ಮೊದಲು,
  webhooks ಮಾಡುವಂತೆಯೇ, `parseAndValidateWebhookUrl`
  (`src/shared/network/outboundUrlGuardPolicy.ts`) ಮೂಲಕ ಅದನ್ನು validate ಮಾಡಬೇಕು. BigQuery ಗೆ ಇದರ ಅಗತ್ಯವಿಲ್ಲ:
  ಅದರ hosts ಸ್ಥಿರಾಂಕಗಳಾಗಿವೆ.

## 6. ಇದನ್ನು ಕಾರ್ಯಾಚರಿಸುವುದು

- **Dashboard**: Integrations → Log export. ಒಂದು ಗಮ್ಯಸ್ಥಾನವನ್ನು ಸೇರಿಸಿ, rows ಅನ್ನು ಬರೆಯದೆಯೇ credentials ಅನ್ನು
  ಪರಿಶೀಲಿಸಲು **Test** ಅನ್ನು ಚಲಾಯಿಸಿ, ನಂತರ ಅದನ್ನು enable ಮಾಡಿ.
- **Backlog**: ಪ್ರತಿಯೊಂದು ಗಮ್ಯಸ್ಥಾನದ card ಬಾಕಿ ಇರುವ rows ಮತ್ತು cursor ಅನ್ನು ತೋರಿಸುತ್ತದೆ; `GET
/api/log-export/status` ಅದೇ ಅಂಕಿಅಂಶಗಳ ಜೊತೆಗೆ ಕೊನೆಯ 20 job runs ಅನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತದೆ.
- **ಒಂದು ಗಮ್ಯಸ್ಥಾನದ ವೈಫಲ್ಯವು ಇತರವುಗಳನ್ನು ವಿಫಲಗೊಳಿಸುವುದಿಲ್ಲ** — run summary ಪ್ರತಿ ಗಮ್ಯಸ್ಥಾನದ
  status ಅನ್ನು `last_status` / `last_error` ನಲ್ಲಿ ದಾಖಲಿಸುತ್ತದೆ ಮತ್ತು job run history ಒಟ್ಟು ಫಲಿತಾಂಶವನ್ನು ಉಳಿಸಿಕೊಳ್ಳುತ್ತದೆ.
- **ಗಮ್ಯಸ್ಥಾನವನ್ನು ಅಳಿಸುವುದರಿಂದ ಅದರ cursor ಕೂಡ ಅಳಿಸಲ್ಪಡುತ್ತದೆ.** ಅದನ್ನು ಮರುಸೇರಿಸಿದಾಗ, ಉಳಿಸಿಕೊಂಡಿರುವ ಅತ್ಯಂತ ಹಳೆಯ
  call log ನಿಂದ ಪ್ರಾರಂಭವಾಗುತ್ತದೆ; ಇದರಿಂದ ಗಮ್ಯಸ್ಥಾನದಲ್ಲಿ ಈಗಾಗಲೇ ಇರಬಹುದಾದ rows ಮತ್ತೆ ಕಳುಹಿಸಲ್ಪಡುತ್ತವೆ. BigQuery ನಲ್ಲಿ ಪ್ರತಿ row ಗೆ ಇರುವ
  `insertId`, BigQuery ನ ಸ್ವಂತ de-duplication window ಒಳಗೆ ಮಾತ್ರ ಇದನ್ನು ನಿಭಾಯಿಸುತ್ತದೆ; ಆದ್ದರಿಂದ ಗಮ್ಯಸ್ಥಾನವನ್ನು ಅಳಿಸುವುದಕ್ಕಿಂತ
  disable ಮಾಡುವುದಕ್ಕೆ ಆದ್ಯತೆ ನೀಡಿ.
