การส่งออกบันทึกการเรียกของ OmniRoute ไปยังคลังข้อมูลวิเคราะห์ภายนอกอย่างต่อเนื่องและเป็นส่วนเพิ่ม

แท็บแดชบอร์ด Logs เก็บประวัติคำขอไว้ใน SQLite (`call_logs`) ซึ่งมีขอบเขตจำกัดด้วย
การหมุนเวียนและระยะเวลาการเก็บรักษา การส่งออกบันทึกจะส่งชุดระเบียนเดียวกันออกไปตามกำหนดเวลา เพื่อให้ข้อมูลมีอายุยาวนานกว่า
ฐานข้อมูลภายในเครื่องและสามารถนำไปรวมกับข้อมูลอื่นได้ BigQuery เป็นปลายทางแรก ส่วน
ไปป์ไลน์เป็นรีจิสทรี ดังนั้นจึงสามารถเพิ่มปลายทางอื่นได้

## 1. วิธีการทำงาน

```
เซิร์ฟเวอร์ (ถอดรหัส + ตรวจสอบความถูกต้องของการกำหนดค่า, ปรับเคอร์เซอร์ให้สอดคล้อง)
  → เริ่ม IPC → โปรเซส OS exportChild แบบแยกส่วน
    → storage.sqlite แบบอ่านอย่างเดียว → คิวรี/การแมป call-log ที่ใช้ร่วมกัน
      → เติมข้อมูลอาร์ติแฟกต์แบบอะซิงโครนัส → prepare()/send() ของปลายทาง
        → IPC แบบแบตช์ → เซิร์ฟเวอร์บันทึกเคอร์เซอร์ → IPC ตอบรับ
          → แบตช์ถัดไป; IPC แจ้งเสร็จสิ้น → เซิร์ฟเวอร์บันทึกความสำเร็จ
```

- **กำหนดเวลา** — งาน cron ของ `JobRegistry` หนึ่งงานชื่อ `log_export` ซึ่งมีค่าเริ่มต้นเป็น `0 * * * *` (ทุกชั่วโมง
  ตามเวลา UTC) ลงทะเบียนใน `src/lib/initCloudSync.ts`; สามารถแทนที่ได้ด้วย `OMNIROUTE_LOG_EXPORT_CRON`
  ในแต่ละรอบจะระบายข้อมูลของทุกปลายทางที่ **เปิดใช้งาน** ตามลำดับ
- **เคอร์เซอร์** — ใช้ `call_logs.rowid` โดยนัยของ SQLite ซึ่งบันทึกแยกตามปลายทางไว้ใน
  `log_export_destinations.cursor_row_id` โดยตั้งใจไม่ใช้ `timestamp` เป็นเคอร์เซอร์ เนื่องจากผู้เรียก
  อาจกำหนดค่าของตนเองได้ ดังนั้นคำขอที่ช้าอาจถูกเขียนหลังคำขอที่เร็วกว่าแต่เริ่มภายหลัง
  และเคอร์เซอร์แบบประทับเวลาจะข้ามคำขอนั้นไป
- **การแบ่งแบตช์** — `batch_size` แถวต่อคำขอ (ค่าเริ่มต้น 500), `max_rows_per_run` แถวต่อการทำงานหนึ่งรอบ
  (ค่าเริ่มต้น 10000) เพื่อให้รายการค้างจำนวนมากทยอยถูกระบายในหลายรอบ แทนที่จะบล็อกอยู่ในรอบเดียว
- **การส่งข้อมูล** — เคอร์เซอร์จะเลื่อนไปข้างหน้าหลังจาก `send()` ทำงานสำเร็จแล้วเท่านั้น แบตช์ที่ล้มเหลวจะทำให้
  เคอร์เซอร์คงอยู่ที่เดิม จึงมีการลองส่งแถวเดิมอีกครั้งในการทำงานรอบถัดไป การรับประกันคือ
  ส่งอย่างน้อยหนึ่งครั้งพร้อมการขจัดข้อมูลซ้ำที่ฝั่งปลายทาง ไม่ใช่แบบครั้งเดียวอย่างแท้จริง โดย BigQuery กำหนดคีย์ของแต่ละ
  แถวด้วย id ของ call-log ซึ่งระบบจะพยายามเคารพแบบดีที่สุดภายในช่วงเวลาขจัดข้อมูลซ้ำของตนเอง
- **ตัวป้องกันการทำงานซ้อน** — รอบ cron และ `POST .../run` อาจทำงานพร้อมกันได้ ปลายทางที่
  กำลังระบายข้อมูลอยู่แล้วจะถูกข้ามแทนที่จะถูกระบายซ้ำสองครั้ง (`skipped: true` ในผลลัพธ์การทำงาน)
  ดังนั้นการทำงานพร้อมกันจึงไม่สามารถส่งแบตช์ซ้ำหรือเขียนเคอร์เซอร์ย้อนกลับได้
- **การกู้คืนหลังการล้างข้อมูล** — หาก `cursor_row_id` มีค่าสูงกว่า `MAX(rowid)` (ตารางทั้งหมดถูก
  ล้างและ rowid เริ่มต้นใหม่) ตัวรันเนอร์จะย้อนกลับไปที่ 0 แทนที่จะมองไม่เห็นข้อมูลอย่างถาวร

### ตัวรันเนอร์แบบแยกส่วนและขีดจำกัด

การทำงานของแต่ละปลายทางบน Node จะเริ่มโปรเซสลูกของ OS ที่แยกต่างหากและมีอายุสั้น (`child_process`
พร้อม IPC ไม่ใช่ `worker_threads`) การอ่าน body, การแยกวิเคราะห์/ซีเรียลไลซ์ payload JSON, `prepare()`
ของปลายทาง และ I/O เครือข่ายของปลายทางทั้งหมดทำงานอยู่ในโปรเซสนั้น ไม่ใช่ใน event loop ของเซิร์ฟเวอร์
มีเพียงการกำหนดค่าและข้อความความคืบหน้าขนาดเล็กเท่านั้นที่ส่งผ่าน IPC; ระเบียนที่ส่งออกจะไม่ย้อนกลับมายัง
เซิร์ฟเวอร์ งาน cron และเส้นทาง Run now ยังคงใช้ผลลัพธ์สาธารณะและตัวป้องกันการทำงานซ้อนแบบเดิม

โปรเซสลูกเปิด `DATA_DIR/storage.sqlite` ที่เซิร์ฟเวอร์ได้ resolve แล้วในโหมดอ่านอย่างเดียวโดยใช้ `node:sqlite`
พร้อม `busy_timeout=5000` และ `query_only=ON` โดยไม่นำเข้า DB singleton และไม่ดำเนินการ
ย้ายข้อมูล สำรองข้อมูล หรืออัปเดต SQLite การจัดการบันทึกเกี่ยวกับอาร์ติแฟกต์ที่สูญหาย/เสียหาย (รวมถึง
UPDATE สำหรับอาร์ติแฟกต์ที่เสียหาย) ยังคงอยู่เฉพาะในเส้นทางรายละเอียดของแดชบอร์ด ทั้งสองเส้นทางใช้ตัว resolve
รายละเอียดแบบ pure ร่วมกัน; การส่งออกใช้การอ่านระบบไฟล์แบบอะซิงโครนัส และใช้ลำดับการ resolve เดียวกันคือ
อาร์ติแฟกต์ → inline แบบเดิม → ดิสก์แบบเดิม → ไม่มี เมื่อโปรเซสลูกเปิดตัวอ่าน การทำงานหนึ่งรอบจะบันทึกภาพรวม
ของ rowid การแทรกสูงสุดไว้; การแทรกภายหลังจะรอจนถึงการทำงานรอบถัดไป นี่คือขอบเขตการแทรก
ไม่ใช่ธุรกรรม SQLite ที่ทำงานยาวนาน: ตัวเขียน WAL และ checkpoint ยังคงทำงานได้อย่างอิสระระหว่าง
การรอเครือข่าย การอัปเดต/ลบแถวที่มีอยู่ไม่ได้ถูกตรึงด้วยขอบเขตนี้

หลังจากแต่ละแบตช์ได้รับการยอมรับ โปรเซสลูกจะรอการตอบรับ เซิร์ฟเวอร์จะบันทึก
เคอร์เซอร์ด้วย `advanceLogExportCursor` ก่อน แล้วจึงส่ง `ack`; จะไม่มีการเริ่มแบตช์ถัดไปก่อนถึงขั้นตอนดังกล่าว
ความล้มเหลวในการส่ง การขัดข้อง หรือการหมดเวลาจะถูกบันทึกเป็นความล้มเหลวโดยไม่เลื่อนเคอร์เซอร์ของแบตช์นั้น
แบตช์ที่ได้รับการตอบรับก่อนหน้านี้จะยังคงถูก commit ไว้; มีเพียงแบตช์ที่ยังไม่ได้รับการตอบรับหนึ่งแบตช์เท่านั้นที่อาจถูกส่งซ้ำ
ระบบจะบันทึกความสำเร็จหลังจากได้รับ `done` และโปรเซสลูกจบการทำงานอย่างสมบูรณ์เท่านั้น เมื่อเกิดความล้มเหลว
โปรเซสลูกจะถูกยุติด้วย SIGTERM และยกระดับเป็น SIGKILL หลังจาก 500 ms จากนั้นตัวรันเนอร์จะรอให้โปรเซสปิดลง

| ตัวแปรสภาพแวดล้อม                             | ค่าเริ่มต้น | วัตถุประสงค์                                   |
| --------------------------------------------- | ----------- | ---------------------------------------------- |
| `OMNIROUTE_LOG_EXPORT_RUN_TIMEOUT_MS`         | 900000      | ขีดจำกัดเวลาจริงต่อปลายทาง                     |
| `OMNIROUTE_LOG_EXPORT_CHILD_MAX_OLD_SPACE_MB` | 1024        | ขีดจำกัด old-space ของ V8 ในโปรเซสลูก หน่วย MB |

ค่าที่ไม่ถูกต้อง/ไม่เป็นบวก/ไม่ใช่จำนวนเต็มจะใช้ค่าเริ่มต้น การตั้งค่า heap ไม่ใช่ขีดจำกัด
RSS ทั้งหมด; แบตช์ที่มีขนาดใหญ่มากยังคงอาจใช้หน่วยความจำของโปรเซสลูกจนหมดและทำให้การทำงานล้มเหลวอย่างปลอดภัย
ค่าเริ่มต้น 1024 MB เว้นพื้นที่สำรองไว้สำหรับแบตช์เริ่มต้นขนาด 500 แถวที่มีอาร์ติแฟกต์ขนาด 512 KiB และ
เปิดใช้งาน body รวมถึงการซีเรียลไลซ์ JSON แบบแบ่งเป็นส่วนไบต์ของ BigQuery ค่านี้ไม่ได้ทำให้
แบตช์ body ขนาด 10000 แถวปลอดภัย การใช้ heap ของ V8 จนหมดจะบันทึกความล้มเหลวที่ดำเนินการแก้ไขได้: ลดขนาดแบตช์
หรือเพิ่ม `OMNIROUTE_LOG_EXPORT_CHILD_MAX_OLD_SPACE_MB`; เคอร์เซอร์จะคงอยู่ที่แบตช์ล่าสุด
ที่ได้รับการตอบรับ body แบบ inline/ดิสก์ในอดีตไม่ได้อยู่ภายใต้ขีดจำกัดอาร์ติแฟกต์สมัยใหม่
ผู้ปฏิบัติงานต้องจัดสรร RSS แยกต่างหาก โดยเฉพาะภายในคอนเทนเนอร์ที่จำกัดหน่วยความจำ

โปรเซสลูกจะรับช่วงต่อเฉพาะ `DATA_DIR` ที่ resolve แล้ว, `NODE_ENV`, `TZ` ที่ระบุอย่างชัดเจน (สำหรับการ resolve
เวลาท้องถิ่นของชื่อไฟล์แบบเดิม), `ELECTRON_RUN_AS_NODE` เมื่อมีอยู่ และอินพุตขาออกต่อไปนี้:
`HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, `NO_PROXY` (รวมถึงรูปแบบตัวพิมพ์เล็ก),
`OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS`, `NODE_EXTRA_CA_CERTS`, `SSL_CERT_FILE`, `SSL_CERT_DIR`
dispatcher ส่วนกลางของ Undici ใช้การ resolve พร็อกซีจากสภาพแวดล้อมแบบ pure และกฎการข้ามโฮสต์ภายในร่วมกับเซิร์ฟเวอร์
รวมถึง `NO_PROXY`; โดยไม่นำเข้า `proxyFetch.ts` หรือ DB/feature flags ของไฟล์ดังกล่าว
ข้อมูลประจำตัวของพร็อกซีจะถูกปกปิดจากเอาต์พุตที่ส่งต่อและข้อผิดพลาดที่บันทึกไว้ ข้อมูลประจำตัวของปลายทาง
จะเดินทางผ่านข้อความ IPC เริ่มต้นเพียงข้อความเดียวเท่านั้น และจะไม่อยู่ใน argv หรือสภาพแวดล้อม; การส่งต่อเอาต์พุต/ข้อผิดพลาดจะ
มีคำนำหน้าและผ่านการทำให้ปลอดภัย เฉพาะ `ExperimentalWarning` เท่านั้นที่ถูกปิดใช้งานในอาร์กิวเมนต์การเรียกใช้ของโปรเซสลูก เพื่อหลีกเลี่ยง
การแสดงคำเตือน SQLite ของ Node ซ้ำทุกครั้งที่ cron ทำงาน; คำเตือนประเภทอื่นยังคงมองเห็นได้

โมดูลปลายทางต้องสามารถนำเข้าได้โดยไม่ต้องพึ่งพา Next.js หรือ dependency ที่ใช้ได้เฉพาะฝั่งเซิร์ฟเวอร์ การทำงานของ
BigQuery ที่มีอยู่เป็นไปตามข้อกำหนดนี้แล้ว แคช access token จะคงอยู่เฉพาะระหว่างการรันของ child
ครั้งนั้น ไม่ได้คงอยู่ข้ามการรัน Node คือ runtime ที่รองรับ (`package.json` engines) แต่ส่วนการติดตั้ง Bun
ใน README และ `Dockerfile.bun` ยังระบุเส้นทางความเข้ากันได้สำหรับ production ที่ใช้
`bun:sqlite` (`src/lib/db/core.ts` / adapters) ดังนั้น เมื่อทำงานภายใต้ Bun การส่งออกจะยังคงใช้เส้นทาง
ภายในโปรเซสแบบเดิม และแสดงคำเตือนหนึ่งครั้งว่าไม่สามารถแยก child heap/timeout ได้ ให้ใช้
Node สำหรับการแยก event loop และ OOM โดยในที่นี้ Bun ไม่ได้ถูกถือว่าใช้เฉพาะสำหรับการพัฒนา

เมื่อเปิดใช้ `includeBodies` ควรใช้รอบการทำงานระดับนาที เช่น
`OMNIROUTE_LOG_EXPORT_CRON="*/5 * * * *"` แทนการสะสม payload ค้างไว้เป็นรายชั่วโมง
ขีดจำกัดของ batch และแถวยังคงจำกัดการรันแต่ละครั้ง การเริ่มต้นโปรเซสมีต้นทุนต่อปลายทางต่อการรัน
วิธีนี้แลกต้นทุนการเริ่มต้นเพียงเล็กน้อยกับการแยก event loop ของเซิร์ฟเวอร์ ไม่ใช่การลดการใช้ CPU โดยรวม

### Payload (prompt และ completion)

โดยค่าเริ่มต้น การส่งออกจะมีเฉพาะฟิลด์สรุปที่แสดงในหน้า **รายการ** ของ Logs การเปิด
**ส่งออก prompt และ response** (`includeBodies`) จะส่งข้อมูลเพิ่มเติมตามที่บานหน้าต่าง
**รายละเอียด** ของ Logs แสดงสำหรับแต่ละ call:

| ฟิลด์                            | ข้อมูลที่จัดเก็บ                                            |
| -------------------------------- | ----------------------------------------------------------- |
| `request_body` / `response_body` | payload ของ call ตามที่ dashboard แสดงผล                    |
| `pipeline_route_decision`        | target และ model ที่ router เลือก                           |
| `pipeline_client_request`        | request ดิบตรงตามที่ client ส่งมา                           |
| `pipeline_openai_request`        | ข้อมูลหลังแปลงเป็นรูปแบบ OpenAI ภายใน                       |
| `pipeline_provider_request`      | ข้อมูลตามที่ส่งไปยัง upstream จริงใน dialect ของ provider   |
| `pipeline_provider_response`     | response ดิบจาก upstream                                    |
| `pipeline_client_response`       | ข้อมูลที่ส่งกลับไปยัง caller                                |
| `pipeline_error`                 | รายละเอียด error ระดับ pipeline สำหรับ call ที่ล้มเหลว      |
| `bodies_truncated`               | เป็น True เมื่อฟิลด์ใดก็ตามด้านบนถึงขีดจำกัด `maxBodyBytes` |

ข้อมูลนี้คือเนื้อหา prompt จึง **ปิดไว้โดยค่าเริ่มต้น** และตั้งใจให้เลือกได้แยกตามแต่ละปลายทาง
ข้อมูลที่ส่งออกคือข้อมูลเดียวกับที่ dashboard แสดง เนื่องจากการส่งออกและ `getCallLogById` ใช้การค้นหา
รายละเอียดร่วมกัน โดย payload จะได้รับการลบข้อมูล PII และปกปิดข้อมูลลับตั้งแต่ตอนที่เขียนข้อมูล
และ call ที่ทำด้วย API key ซึ่งตั้งค่า `noLog` จะไม่จัดเก็บ payload ใดๆ เลย จึงไม่มีข้อมูลให้ส่งออก

ระบบจะอ่าน payload ของแต่ละแถวจาก artifact ใน filesystem ดังนั้น hydration จะทำงานเฉพาะกับปลายทาง
ที่ร้องขอเท่านั้น หาก artifact สูญหายหรือเสียหาย ระบบจะส่งออกข้อมูลสรุปพร้อม payload ที่เป็น null
แทนที่จะทำให้ทั้ง batch ล้มเหลวและทำให้ cursor ค้างอยู่

`maxBodyBytes` (ค่าเริ่มต้นคือ 262144) จำกัดขนาดของแต่ละฟิลด์ payload ที่ยาวกว่านี้จะถูก
**ตัดทอนแทนที่จะทิ้ง** — prompt ที่ถูกตัดยังคงตอบคำถามว่า "มีการถามอะไร" ได้ — และแถวนั้นจะถูกระบุด้วย
`bodies_truncated` ระบบจะไม่ส่งออก delta แบบ streamed ทีละ chunk เนื่องจาก response ที่ประกอบเสร็จแล้ว
มีอยู่ใน `pipeline_provider_response` และ `pipeline_client_response` อยู่แล้ว

ทุกเส้นทางผ่านการยืนยันตัวตนสำหรับการจัดการ (`requireManagementAuth`) ระบบจะไม่ส่งคืนข้อมูลลับ:
ข้อมูลลับที่จัดเก็บไว้จะถูกส่งกลับเป็นค่าตรงตัว `__stored__` และการส่งค่านี้กลับมาในการอัปเดต

## 4. ปลายทาง BigQuery

คีย์การกำหนดค่า (`type: "bigquery"`):

| คีย์                 | หมายเหตุ                                                       |
| -------------------- | -------------------------------------------------------------- |
| `projectId`          | โปรเจกต์ GCP ที่มีชุดข้อมูลอยู่                                |
| `datasetId`          | `[A-Za-z0-9_]+`                                                |
| `tableId`            | `[A-Za-z0-9_]+`                                                |
| `location`           | ใช้เฉพาะเมื่อต้องสร้างชุดข้อมูล (ค่าเริ่มต้น `EU`)             |
| `serviceAccountJson` | คีย์บัญชีบริการ ข้อมูลลับ: เข้ารหัสขณะจัดเก็บและไม่ส่งคืน      |
| `autoCreate`         | สร้างชุดข้อมูลและตารางในการส่งออกครั้งแรก (ค่าเริ่มต้น `true`) |

บัญชีบริการต้องมีสิทธิ์ `bigquery.tables.updateData` บนตารางเป้าหมาย รวมถึง
`bigquery.datasets.create` / `bigquery.tables.create` เมื่อเปิด `autoCreate`

ชุดข้อมูลที่กำหนดค่าไว้เป็นหน่วยของ **เคอร์เซอร์** ไม่ใช่หน่วย HTTP: `send()` จะแบ่งชุดข้อมูลออกเป็นการเรียก insertAll
ครั้งละไม่เกิน 500 แถว ดังนั้น `batch_size` ขนาดใหญ่จึงไม่ทำให้เกินขีดจำกัดคำขอ 10 MB ของ BigQuery
สถานะชั่วคราว (408/429/500/502/503/504) จะถูกลองใหม่สูงสุดสามครั้งด้วยการหน่วงเวลาแบบเอ็กซ์โพเนนเชียล
โดยใช้ insertIds เดิมซ้ำ ส่วนข้อผิดพลาดด้านการยืนยันตัวตนและสคีมาจะ throw ตั้งแต่ครั้งแรก แทนที่จะ
ใช้รอบการทำงานไปโดยเปล่าประโยชน์

ตารางที่เพิ่งสร้างเมื่อไม่กี่วินาทีก่อนยังไม่ปรากฏต่อเอนด์พอยต์สตรีมมิง ซึ่งจะตอบกลับ
404 เป็นเวลาสองสามวินาที ระบบจะลองใหม่เมื่อได้รับ 404 แต่ **เฉพาะเมื่อการทำงานรอบนี้เป็นผู้สร้างตาราง** เท่านั้น —
ตารางที่ไม่มีอยู่จริงจะยังคงล้มเหลวทันที โปรดทราบว่าการสร้างตารางใหม่โดยใช้ชื่อที่เพิ่งถูกลบไป
จะทำให้ BigQuery ปฏิเสธการแทรกข้อมูลแบบสตรีมมิงเป็นเวลาหลายนาที ซึ่งเป็นคุณสมบัติของการลบแล้วสร้างใหม่
ดังนั้นควรใช้ชื่อตารางใหม่แทนการลบแล้วเพิ่มตารางเดิมกลับเข้ามา

**ความล้มเหลวบางส่วนจะมาในรูปแบบ HTTP 200 พร้อม `insertErrors[]` ที่ไม่ว่างเปล่า** ระบบจะถือว่า
นี่เป็นความล้มเหลวและ throw ซึ่งจะหยุดไม่ให้เคอร์เซอร์เลื่อนผ่านแถวที่ BigQuery ไม่เคย
ยอมรับ โดย `tests/unit/log-export-bigquery.test.ts` จะตรึงพฤติกรรมนี้ไว้

การรับส่งข้อมูลใช้ REST โดยตรง — assertion แบบ RS256 ที่ลงนามด้วยตนเองจะถูกแลกเป็นโทเค็นการเข้าถึงที่
`https://oauth2.googleapis.com/token` จากนั้นแถวข้อมูลจะถูกส่งไปยัง `tabledata.insertAll` ไม่มีการดึง
Google SDK เข้ามาใช้ โทเค็นการเข้าถึงจะถูกแคชภายในโปรเซสแยกตามคู่ (บัญชีบริการ, ขอบเขต)

ตารางที่สร้างขึ้นจะมีหนึ่งคอลัมน์ต่อหนึ่งฟิลด์ในแท็บ Logs รวมถึง `exported_at` และถูกจัดวางให้เหมาะกับ
รูปแบบการคิวรีบันทึกการเรียกใช้งานจริง:

- **แบ่งพาร์ทิชันรายวันตาม `timestamp`** ดังนั้นคิวรีที่จำกัดขอบเขตด้วยวันที่จะสแกนเฉพาะวันเหล่านั้น
- **คลัสเตอร์ตาม `api_key_name`, `provider`, `model`, `status`** (ตามลำดับนี้) ดังนั้นการกรองตาม
  ผู้ที่เรียกใช้ ปลายทางที่ส่งไป หรือสถานะว่าล้มเหลวหรือไม่ จะช่วยตัดบล็อกภายในแต่ละพาร์ทิชันออก BigQuery
  อนุญาตคอลัมน์คลัสเตอร์ได้สูงสุดสี่คอลัมน์และลำดับมีความสำคัญ: การกรองเฉพาะ `api_key_name`
  ช่วยตัดบล็อกได้ แต่การกรองเฉพาะ `status` ทำไม่ได้
- **การเก็บรักษาพาร์ทิชันแบบเลือกได้** ผ่าน `partitionExpirationDays` (0 หมายถึงเก็บทุกอย่างไว้) ซึ่งจะถูกนำไปใช้
  เมื่อสร้างตาราง

การตั้งค่าทั้งสองมีผลในขณะสร้าง ตารางที่มีอยู่แล้วจะคงรูปแบบเดิมไว้ ดังนั้น
หากต้องการใช้การตั้งค่าเหล่านี้ ให้กำหนดปลายทางไปยัง id ของตารางใหม่

`tests/unit/log-export-bigquery.test.ts` ตรวจสอบว่า mapper และสคีมาของตารางสอดคล้องกันอยู่เสมอ
ดังนั้นคอลัมน์ call-log ใหม่จะไม่ถูกละทิ้งโดยไม่มีการแจ้งเตือนระหว่างการส่งออก

แบตช์จะถูกแบ่งเป็นส่วนย่อยตาม **ทั้ง** จำนวนแถวและจำนวนไบต์หลังการแปลงเป็นข้อมูลแบบลำดับ จำนวนแถวเพียงอย่างเดียวนั้นไม่เพียงพอ
เมื่อมีการส่งออก payload: 500 แถวที่มี prompt อาจมีขนาดหลายสิบเมกะไบต์ และ insertAll
จะปฏิเสธคำขอที่มีขนาดเกิน 10 MB แต่ละส่วนย่อยจะสิ้นสุดเมื่อครบ 500 แถวหรือมีขนาดถึง 9 MB แล้วแต่ว่าเงื่อนไขใดจะเกิดขึ้นก่อน

## 5. การเพิ่มปลายทาง

1. สร้าง `src/lib/logExport/destinations/<name>.ts` ซึ่งส่งออก `LogExportDestinationType`:
   โดยมี `configSchema` ของ Zod, อาร์เรย์ตัวอธิบาย `fields` สำหรับ UI, `secretFields` และ
   `createClient(config)` ที่คืนค่า `test()` / `prepare()` / `send(records)`
2. เพิ่มรายการดังกล่าวลงในอาร์เรย์ `DESTINATIONS` ใน `src/lib/logExport/registry.ts`
3. เขียนการทดสอบไว้ภายใต้ `tests/unit/`

การเปลี่ยนแปลงมีเพียงเท่านี้: ส่วนการจัดเก็บข้อมูล งาน cron เลเยอร์ REST การเข้ารหัสข้อมูลลับ และ
แบบฟอร์มแดชบอร์ด ล้วนอ้างอิงรีจิสทรี

กฎสองข้อสำหรับปลายทางใหม่:

- `send()` **ต้อง throw** เมื่อเกิดความล้มเหลวบางส่วน การ resolve หมายความว่า "ปลายทางมีแถวเหล่านี้แล้ว"
  และเคอร์เซอร์จะเลื่อนผ่านแถวเหล่านั้นอย่างถาวร
- ปลายทางที่รับ URL จากผู้ใช้ต้องตรวจสอบ URL ผ่าน
  `parseAndValidateWebhookUrl` (`src/shared/network/outboundUrlGuardPolicy.ts`) ก่อนทำการ fetch
  เช่นเดียวกับที่ webhook ทำ ส่วน BigQuery ไม่จำเป็นต้องทำเช่นนี้ เนื่องจากโฮสต์ของ BigQuery เป็นค่าคงที่

## 6. การใช้งาน

- **แดชบอร์ด**: Integrations → Log export เพิ่มปลายทาง เรียกใช้ **Test** เพื่อตรวจสอบข้อมูลประจำตัว
  โดยไม่เขียนแถวข้อมูล จากนั้นเปิดใช้งานปลายทาง
- **งานค้าง**: การ์ดของแต่ละปลายทางจะแสดงแถวที่รอดำเนินการและเคอร์เซอร์ ส่วน `GET
/api/log-export/status` จะส่งคืนตัวเลขเดียวกันพร้อมกับประวัติการทำงาน 20 ครั้งล่าสุด
- **ปลายทางหนึ่งที่ล้มเหลวจะไม่ทำให้ปลายทางอื่นล้มเหลว** — สรุปการทำงานจะบันทึกสถานะของแต่ละปลายทาง
  ไว้ใน `last_status` / `last_error` และประวัติการทำงานจะเก็บผลรวมโดยรวมไว้
- **การลบปลายทางจะลบเคอร์เซอร์ของปลายทางนั้นด้วย** การเพิ่มปลายทางนั้นกลับเข้ามาใหม่จะเริ่มจาก
  บันทึกการเรียกที่เก่าที่สุดซึ่งยังคงเก็บรักษาไว้ ทำให้มีการส่งแถวที่ปลายทางอาจมีอยู่แล้วซ้ำอีกครั้ง
  สำหรับ BigQuery ค่า `insertId` ของแต่ละแถวจะจัดการข้อมูลซ้ำได้เฉพาะภายในช่วงเวลาการขจัดข้อมูลซ้ำ
  ของ BigQuery เองเท่านั้น ดังนั้นควรปิดใช้งานปลายทางแทนการลบ
