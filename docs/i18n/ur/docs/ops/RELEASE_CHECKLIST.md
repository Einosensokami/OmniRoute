## npm Trusted Publishing (v3.8.51 سے ڈیفالٹ) — درخواست پر مرحلہ وار، بصورت دیگر براہِ راست

`npm-publish.yml` ڈیفالٹ طور پر **npm Trusted Publishing (OIDC)** کے ذریعے شائع کرتا ہے:
`stage-npm` جاب (github-hosted) اس رَن کے لیے GitHub کے id-token کو مختصر مدت کی npm
اسناد سے تبدیل کرتی ہے — repository secrets میں کوئی طویل مدتی npm ٹوکن نہیں، کوئی 2FA پرامپٹ نہیں، اور provenance منسلک ہوتا ہے۔
اب جبکہ npm ایسے ٹوکنز کو ختم کر رہا ہے جو 2FA کو نظر انداز کرتے ہیں، یہی npm کا منظور شدہ متبادل ہے؛
یہ WS1.3 کی ضمانت برقرار رکھتے ہوئے اس مکمل خودکار فلو کو بحال کرتا ہے جو پروجیکٹ میں v3.8.48 تک موجود تھا
(لیک شدہ ٹوکن اکیلا شائع نہیں کر سکتا — کیونکہ کوئی ٹوکن موجود ہی نہیں ہے)۔

**ایک بار کا سیٹ اپ (مالک):** npmjs.com → package `omniroute` → Settings → _Trusted
Publisher_ → GitHub: owner `diegosouzapw`، repo `OmniRoute`، workflow `npm-publish.yml`
(environment: none)۔ اس کے موجود ہونے تک خودکار مرحلہ `ENEEDAUTH` کے ساتھ ناکام ہوگا:
`publish_mode=staged` (ذیل میں) یا `direct` کے ساتھ دوبارہ dispatch کریں۔

### مرحلہ وار اشاعت (درخواست پر — `publish_mode=staged`)

npm-publish workflow اب براہِ راست شائع نہیں کرتا: یہ پیک شدہ tarball کو بوٹ کرتا ہے
(`check:pack-boot`) اور پھر `npm stage publish` چلاتا ہے — بعینہٖ وہی bytes registry پر رکھ دی جاتی ہیں،
مگر مالک کی منظوری تک **انسٹال نہیں کی جا سکتیں**۔ انسانی 2FA گیٹ اب ثبوت سے پہلے نہیں بلکہ
اس کے بعد آتا ہے۔

**workflow کے گرین ہونے کے بعد مالک کا فلو:**

1. `npm stage list omniroute` — stage id تلاش کریں (یہ workflow summary میں بھی پرنٹ ہوتی ہے)۔
2. مرحلہ وار رکھی گئی bytes کی تصدیق کریں (تجویز کردہ): `npm stage download <id>`، پھر ڈاؤن لوڈ شدہ
   tarball کو ایک عارضی prefix میں انسٹال کر کے بوٹ کریں (`npm run check:pack-boot`، CI میں اسی
   pack→install→boot فیصلے کو خودکار بناتا ہے)۔
3. `npm stage approve <id>` — 2FA پرامپٹ ہی اشاعت ہے۔ `npm stage reject <id>` اسے مسترد کر دیتا ہے۔
4. اشاعت کے بعد حفاظتی جانچ: post-publish verifier (v3.8.49 پلان کا WS1.4) ایک صاف container میں
   public registry سے شائع شدہ ورژن انسٹال کر کے اسے بوٹ کرتا ہے۔

**ہنگامی متبادل:** `publish_mode=direct` کے ساتھ `workflow_dispatch` پرانا فوری
`npm publish` بحال کرتا ہے (صرف اس صورت میں استعمال کریں جب staging خود درست طور پر کام نہ کرے؛ وجہ درج کریں)۔

**ایک بار کی سخت حفاظتی ترتیب (مالک، npmjs.com):** `omniroute` کے لیے Trusted Publisher کو
stage-only موڈ میں ترتیب دیں، تاکہ لیک شدہ طویل مدتی ٹوکن کہیں سے بھی براہِ راست `npm publish`
نہ کر سکے — CI صرف stage کر سکتا ہے؛ صرف مالک کا 2FA ریلیز کر سکتا ہے۔

**خراب artifact کے لیے طریقۂ کار (بلا تبدیلی):** ڈیفالٹ فوری ردِعمل کے طور پر
`npm deprecate omniroute@<bad> "<reason> — use <fixed>"` استعمال کریں (چند منٹ، قابلِ واپسی)؛
`npm unpublish` صرف 72h/no-dependents ونڈو کے اندر استعمال کریں اور کبھی بھی پہلے اقدام کے طور پر نہیں۔
Docker: کسی version tag کو کبھی دوبارہ نہ لکھیں — rollback کا مطلب `latest` کو آخری درست digest کی طرف دوبارہ اشارہ کرنا ہے۔

**Docker Hub `latest` (ہر مستحکم SemVer اشاعت پر ضروری):**
`docker-publish` workflow کو **دونوں** `X.Y.Z` اور، جب
`should-promote-latest.sh` اس کے بلند ترین مستحکم SemVer ہونے کی تصدیق کرے، `:latest`
کو **اسی digest** کے ساتھ tag کرنا چاہیے۔ جاب کے بعد: Hub کے `latest` کا digest نئے
SemVer digest کے برابر ہو اور `last_updated` آگے بڑھ چکا ہو۔ `:latest` کو کسی پرانے
build پر مت چھوڑیں جبکہ release notes ان اصلاحات کا ذکر کر رہے ہوں جو صرف git میں موجود ہیں۔
Compose quickstarts میں `:latest` استعمال ہوتا ہے؛ GitOps میں `X.Y.Z` کو pin کرنا جاری رکھیں۔
[Docker ریلیز چینلز](../guides/DOCKER_GUIDE.md#release-channels) اور #10317 دیکھیں۔

## ہاٹ فکس فاسٹ لین (لیبل `hotfix`)

`hotfix` لیبل والا PR بھاری CI میٹرکس (9-shard E2E، coverage ratchet،
quality-gate، quality-extended) کو چھوڑ دیتا ہے اور تیز، زیادہ مؤثر گیٹس برقرار رکھتا ہے: build،
unit shards، integration، vitest، lint/typecheck، docs-sync، `check:pack-artifact`
اور tarball boot-smoke (`check:pack-boot`)۔ ہدف: ~33min کے بجائے ≤15min میں گرین۔

**داخلے کی پالیسی — چاروں شرائط لازم ہیں (Chromium/VS Code/Node کی ایمرجنسی لینز کی طرز پر):**

1. **شدت**: پروڈکشن خراب ہے — شائع شدہ artifact بوٹ ہوتے وقت کریش کرتا ہے / کوئی
   سیکیورٹی فکس ہے / ریلیز کا ہر صارف متاثر ہے۔ "اہم" کا مطلب "خراب" نہیں۔
2. **اختیار**: صرف repository کا مالک `hotfix` لیبل لگاتا ہے۔ لیبل ہی
   منظوری ہے — campaign PR پر اسے کبھی خود سے استعمال نہ کریں۔
3. **ثبوت**: PR باڈی میں پچھلی مکمل طور پر گرین بھاری رَن کا لنک شامل ہو (وہ suite جسے
   چھوڑے گئے jobs دوبارہ validate کرتے)، نیز خود فکس کا پہلے ناکام اور پھر کامیاب ہونے والا test۔
4. **دائرۂ کار**: صرف cherry-pick — کم سے کم فکس، کوئی refactors نہیں، کوئی اضافی تبدیلیاں نہیں۔

چھوڑی گئی coverage/ratchet سطح کی اگلے مکمل رَن میں
release branch پر دوبارہ توثیق کی جاتی ہے (مسلسل release-green) — یہ لین صرف انتظار کو چھوڑتی ہے، validation کو کبھی نہیں۔
صرف tests والی diffs (`tests/` کے تحت تمام files، `tests/e2e/` کے تحت کوئی نہیں) بغیر کسی لیبل کے
خودکار طور پر E2E میٹرکس چھوڑ دیتی ہیں۔

### Hooks (Husky سے توثیق شدہ)

Husky hooks، `.husky/` میں موجود ہیں اور git کارروائیوں پر خودکار طور پر چلتے ہیں۔

- **pre-commit:** `npx lint-staged + node scripts/check/check-docs-sync.mjs + npm run check:any-budget:t11`
- **pre-push:** تیز، قطعی gates — `npm run check:any-budget:t11 && npm run check:tracked-artifacts` (2026-06-13 کو فعال کیا گیا)۔ جان بوجھ کر `test:unit` شامل نہیں ہے (سست؛ CI کے `test-unit` job میں شامل ہے)۔
  - ریلیز برانچز push کرنے سے پہلے `npm run test:unit` دستی طور پر چلائیں۔

اگر کوئی hook ناکام ہو جائے: بنیادی مسئلہ حل کریں، `--no-verify` کے ذریعے اسے نظر انداز نہ کریں۔

### روایتی Commits

ریلیز میں شامل ہونے والے تمام commits لازماً `type(scope): subject` فارمیٹ کی پیروی کریں۔

**درست types:** `feat`، `fix`، `refactor`، `docs`، `test`، `chore`، `perf`، `style`، `ci`

### بلڈ کی ساخت

ریپوزٹری تین الگ آؤٹ پٹ ڈائریکٹریز استعمال کرتی ہے — انہیں کبھی آپس میں نہ ملائیں:

| ڈائریکٹری | مقصد                                                           | ٹریک شدہ؟         |
| --------- | -------------------------------------------------------------- | ----------------- |
| `src/`    | ایپلیکیشن سورس (TypeScript / TSX)                              | ہاں               |
| `.build/` | بلڈ کے عبوری نتائج — `next build` آؤٹ پٹ (`distDir`)           | نہیں (gitignored) |
| `dist/`   | قابلِ ترسیل npm بنڈل — `assembleStandalone` کے ذریعے تیار کردہ | نہیں (gitignored) |

> **آپریٹر نوٹ:** ریموٹ VPS امیج ڈائریکٹری بدستور `/usr/lib/node_modules/omniroute/app/` ہے۔
> صرف **ریپوزٹری کے اندر** موجود بلڈ آؤٹ پٹ منتقل ہوا ہے (`app/` → `dist/`)۔ ڈیپلائے اسکلز
> `dist/` کے مواد کو ریموٹ `app/` ڈائریکٹری میں rsync کرتی ہیں — VPS پاتھ میں کسی تبدیلی کی ضرورت نہیں۔

**ایک بلڈ کا فلو:**

```
npm run build:release
  └─ rm -rf .build dist          (صفائی)
  └─ next build → .build/next/   (عبوری نتائج)
  └─ assembleStandalone          (standalone + static + public + natives کو dist/ میں کاپی کرتا ہے)
  └─ writes dist/BUILD_SHA       (HEAD سینٹینل)
```

ڈیپلائے کے لیے `npm run build` چلانے کے بعد الگ سے `npm run build:cli` **نہ** چلائیں — اس کے بجائے
`npm run build:release` استعمال کریں، جو ایک ہی کمانڈ میں صاف ری بلڈ اور سینٹینل تیار کرتا ہے۔

### آزمائشی اجرا (صرف پڑھنے کے لیے، کسی بھی وقت محفوظ)

```bash
npm run release:dry-run-lts-cut                       # اصل کٹ: HEAD سے 3.9.0، پچھلا ٹیگ v3.8.59
npm run release:dry-run-lts-cut -- --from <3.9.0-tip> # ماخذ کمٹ کو پن کریں
```

`scripts/release/dry-run-lts-cut.mjs` کچھ بھی نافذ نہیں کرتا: یہ git اور `gh` کو پڑھتا ہے اور
پورا سلسلہ پرنٹ کرتا ہے — پیشگی شرائط (ماخذ ریزولو ہو، ماخذ ریپوزٹری میں مکمل ہسٹری موجود ہو —
ایک shallow clone، `stable/v3` کو پش نہیں کر سکتا، وصول کنندہ پہلا
grafted parent ملنے پر پیک مسترد کر دیتا ہے، اس لیے مکمل clone سے کٹ کریں یا پہلے
`git fetch --unshallow origin` چلائیں — پچھلا ٹیگ موجود ہو، `package.json` ہدف ورژن پر ہو، ایک
`release-freeze` مسئلہ کھلا ہو، اور موجودہ ریلیز برانچ پر کوئی کھلا
`Release branch not green` مسئلہ نہ ہو — جو برانچ موجود نہ ہو وہ `?` نامعلوم رپورٹ کرتی ہے، کبھی
سبز نہیں — Mergify کی `release` قطار کنفیگر ہو (G11: `queue_rules`، `checks_timeout`،
لیبل `queue`)، `release/*` ruleset اب بھی حذف کرنے اور force-push کو روکتا ہو، اور
`stable/v3` اور `develop` ابھی موجود نہ ہوں)، دونوں برانچ مراحل، یہ کہ کون سے غیر فعال workflow
ٹرگرز اور `if:` شرائط درست ہو جاتی ہیں (اور کون سی کسی ریپوزٹری متغیر کے ذریعے گیٹ رہتی ہیں یا
canonical ریپوزٹری سے پن ہوتی ہیں)، متوقع dist-tags (`latest` → 3.9.0، `next` اور
`nightly` خالی) اور رول بیک۔ خروج `0` = `RESULT: READY`، `1` = کوئی لازمی پیشگی شرط
ناکام ہوئی (`✗`)، `2` = استعمال کی خرابی۔ `--advisory <id,...>` کسی جانچ کو چھپائے بغیر
انتباہ (`!`) میں تبدیل کر دیتا ہے۔

اصل کٹ کا آزمائشی اجرا اس وقت چلائیں جب 3.9.0 کا ریلیز فریز اب بھی کھلا ہو — برانچیں
ٹیگ کے بعد اور مرحلہ 12c میں فریز اٹھائے جانے سے پہلے بنائی جاتی ہیں۔

### 3.8.58 کی مشق (صرف فورک)


### PR پیش منظر آرٹیفیکٹ (ایک بار بنائیں، انہی بائٹس کو پروموٹ کریں)

`.github/workflows/preview-artifact.yml` کسی PR head سے ایک production tarball بناتا ہے اور
اسی عین build کی توثیق کرتا ہے (#8084 حصہ (a))۔ صرف اسی ریپوزٹری کی PRs؛ کچھ بھی شائع نہیں کیا جاتا۔

```bash
gh workflow run preview-artifact.yml -f pr_number=<N>   # یا `preview-artifact` لیبل شامل کریں
gh run download <run-id> --name preview-artifact-pr<N>-<sha7> --dir preview
cd preview && sha256sum -c SHA256SUMS
gh attestation verify omniroute-*.tgz --repo diegosouzapw/OmniRoute
npm install -g ./omniroute-*.tgz                          # پیش منظر کی تنصیب
```

اجرا `npm ci`، `npm run build:release`، `npm run check:pack-artifact` چلاتا ہے، پھر
tarball پیک کرتا ہے، `npm run check:pack-boot` چلاتا ہے (جعلی secrets، عارضی data dir)، دوبارہ پیک کرتا ہے اور
اگر digest یکساں نہ ہو تو ناکام ہو جاتا ہے، پھر `artifact-identity.json` ریکارڈ کرتا ہے (head SHA، base
SHA، lockfile hash، platform، arch، node ABI، bundler، build policy —
`scripts/release/artifact-identity.mjs`) اور ایک الگ job میں tarball کی تصدیق کرتا ہے۔ پیش منظر کو پروموٹ
کرنے کا مطلب اسی tarball کو نصب کرنا ہے: ماخذ سے کبھی دوبارہ build نہ کریں۔

## رول بیک

اگر ریلیز میں کوئی سنگین مسئلہ ہو:

1. `gh release edit vX.Y.Z --prerelease` (اسے تازہ ترین ریلیز نہ ہونے کے طور پر نشان زد کرتا ہے)
2. `git tag -d vX.Y.Z && git push --delete origin vX.Y.Z` (صرف اس صورت میں جب صارفین نے ابھی تک اسے اختیار نہ کیا ہو)
3. یا: `release/vX.Y.0` پر ہاٹ فکس → پیچ ریلیز `vX.Y.(Z+1)`
4. GitHub Discussions اور Discord میں فوری طور پر اطلاع دیں

## سخت اصول

- کبھی بھی براہِ راست `main` میں کمٹ نہ کریں
- `main` یا `release/*` برانچز پر کبھی بھی `git push --force` استعمال نہ کریں
- Husky ہکس (`--no-verify`) کو کبھی نظر انداز نہ کریں
- کبھی بھی راز، اسناد، یا `.env` فائلیں کمٹ نہ کریں
- کوریج ≥60/60/60/60 (اسٹیٹمنٹس/لائنز/فنکشنز/برانچز) برقرار رہنی چاہیے
- `src/`، `open-sse/`، `electron/`، یا `bin/` میں پروڈکشن کوڈ تبدیل کرتے وقت ہمیشہ ٹیسٹس شامل یا اپ ڈیٹ کریں
